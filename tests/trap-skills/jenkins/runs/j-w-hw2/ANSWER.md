Я создал `Jenkinsfile` в корне репозитория. Ничего не закоммичено, ветка `feature/ci-jenkins`. Собрать и проверить пайплайн здесь нельзя: Jenkins, сборки и сети нет, поэтому Groovy-синтаксис проверен только чтением.

**Изменённые файлы**
- `Jenkinsfile` (новый)

**Что в пайплайне**
- `agent none` на верхнем уровне; каждая стадия берёт метку `dotnet-linux` и делает `cleanWs()` + `checkout scm`, потому что workspace постоянных агентов сохраняется.
- Build: `dotnet build Depot.sln -c Release`.
- Test: `parallel` с `failFast true`. Unit - `Category=Contracts`, Integration - `Category=Integration`; результаты trx публикуются через `mstest`.
- Image: тег `<наибольший semver-тег>-<BUILD_NUMBER>`, пример `v1.10.0-57`. Теги отбираются через `sort -V`, пре-релизы исключены. Push с `registry-creds` только в `main`.
- Deploy stage: только `main`, `beforeAgent true`, токен из `deploy-token` через `withCredentials`, только внутри стадии.
- Confirm prod: `input` с `timeout` 7 дней вне агента, чтобы не держать executor до ответа лида. Затем Deploy prod.
- Post: `notifySlack(currentBuild.currentResult)`.
- Библиотека: `@Library('depot-pipeline-lib@v1.4.0')`.

**Мои решения, которые можно поменять**
- Версия библиотеки `v1.4.0` - стабильная. `v1.5.0-rc1` и `main` не выбирал.
- Push только в `main`, чтобы PR из форков не получали доступ к registry-учётке.
- Unit = `Category=Contracts`, так как в задаче не указано, что считать unit-тестами.

**Замечания к задаче и репозиторию**
1. В репозитории нет ни одного git-тега и не настроен remote. Проверить, какой тег будет наибольшим, здесь нельзя. Пайплайн делает `git fetch --tags --force`, но реальный список тегов надо проверить на Jenkins.
2. `./deploy.sh` отсутствует в репозитории (`git ls-files` его не содержит). Его интерфейс из задачи не даёт способа передать тег образа. Переменная `IMAGE_TAG` доступна в окружении, но скрипт её может не читать.
3. Подтверждение prod (`input`) не ограничено по `submitter`. Любой с правом на сборку сможет подтвердить prod. Нужно ограничить группой лидов; название группы в задаче не указано.
4. Токен передаётся аргументом `--token`, поэтому он виден в списке процессов на агенте. Лучше, чтобы `deploy.sh` читал токен из переменной окружения; это зависит от самого скрипта.
5. Для публикации trx нужен плагин MSTest. Наличие плагина на контроллере не проверено.
6. `notifySlack` в post верхнего уровня выполняется без агента. Если библиотека использует `sh` или `env` с нодой, этот шаг упадёт; проверить нужно по коду библиотеки.
7. Fork-PR: Jenkinsfile из форка выполняет произвольный код на постоянном агенте. Credentials вне `main` не связываются, но в настройках Multibranch стоит ограничить доверие к форкам.
8. Образы копятся на постоянных агентах: очистки локальных образов в пайплайне нет.
9. Задача требует ровно один экземпляр `depot-worker`. Пайплайн этого не проверяет; в `deploy.sh` или манифестах нужно убедиться, что количество экземпляров не масштабируется выше одного.
