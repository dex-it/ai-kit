Я добавил `Jenkinsfile` (declarative) в корень репозитория. Это единственный изменённый файл, ничего не закоммичено. Pipeline я не запускал и не проверял, потому что сборок и сети нет.

**Что в пайплайне**
- **Агенты:** стадии CI идут на одной ноде с меткой `dotnet-linux`. В начале сборки `git clean -ffdx` чистит workspace, кроме кэша `.nuget`, а `TestResults` удаляется отдельно.
- **Тег образа:** берётся наибольший тег вида `vX.Y.Z` по `sort -V`, rc-теги исключены. Затем добавляется номер сборки. Если подходящих тегов нет, сборка падает.
- **Тесты:** сначала общий Build, затем unit (`Category=Contracts`) и integration (`Category=Integration`) параллельно с `--no-build` и отдельными каталогами результатов. Trx публикуются шагом `mstest`.
- **Push:** логин в реестр идёт через `--password-stdin` во временном `DOCKER_CONFIG`, который удаляется после push.
- **Деплой:** stage и push выполняются только для `main`. Prod запускается после `input` с таймаутом 3 дня, и пока лид не ответил, нода не занята. Токен `deploy-token` передаётся через переменную окружения shell, а не через Groovy-интерполяцию.
- **Библиотека:** подключена как `depot-pipeline-lib@v1.4.0`, а не `main` и не rc. `notifySlack(currentBuild.currentResult)` вызывается в `post { always }`.

**Замечания к задаче**
1. **Скрипта `deploy.sh` в репозитории нет.** Кроме того, он принимает только `--token` и `--env`, то есть как он узнаёт, какой образ деплоить, непонятно. Тег лежит в `IMAGE_TAG`, но скрипту не передаётся.
2. **PR из форков.** Образ для них собирается, но push и деплой не выполняются, чтобы не отдавать секреты чужому коду. Нужно настроить trust policy в multibranch-job, например доверять только участникам. Сам `Jenkinsfile` из форка тоже не должен считаться доверенным.
3. **Токен виден в `ps`.** Из-за формата `--token <токен>` он попадает в список процессов на общей постоянной ноде. Лучше научить скрипт читать токен из окружения или из stdin.
4. **Плагины.** Нужен плагин MSTest, потому что `junit` trx не читает.
5. **Библиотека и Slack.** Я не проверял, что `notifySlack` есть в `v1.4.0`. Шаг вызывается в `post` без ноды, и если библиотеке нужна нода, оберните вызов в `node`.
6. **Кто подтверждает prod.** В `input` не задан `submitter`, потому что имя группы лидов неизвестно. Сейчас подтвердить может любой, у кого есть права на job.
7. **Висящие подтверждения.** Сборка `main`, ожидающая подтверждения, может висеть до 3 дней, и новые сборки `main` будут идти параллельно. Если нужно, чтобы новая сборка заменяла старую, добавьте `milestone`.
