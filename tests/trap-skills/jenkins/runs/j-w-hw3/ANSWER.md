**Что в пайплайне**
- Верхний `agent none`. Стадии с агентом берут `dotnet-linux` сами, а стадия ожидания подтверждения prod без агента, поэтому ожидание лида не держит executor.
- Сборка → тесты параллельно (`failFast true`; Unit: `Category!=Integration`, Integration: `Category=Integration`, trx публикуются через MSTest) → образ → push → deploy stage → подтверждение (`input`, таймаут 72 часа) → deploy prod.
- Тег `<наибольший semver-тег>-<BUILD_NUMBER>`: сортировка `sort -V` по тегам вида `vX.Y.Z`. Пример: `v1.10.0-42`.
- Учётки через `withCredentials`: `registry-creds` (username/password, пароль в `--password-stdin`), `deploy-token` (secret text, передаётся в `./deploy.sh --token "$DEPLOY_TOKEN"`).
- `cleanWs()` в post каждой стадии с агентом.
- Библиотека `depot-pipeline-lib@v1.4.0`, `notifySlack(currentBuild.currentResult)` в post верхнего уровня.

**Мои решения, которые стоит проверить**
- Push и обе deploy-стадии только на `main`. Учётка реестра и deploy-token не попадают в PR, в том числе из форков. Список задачи буквально не требует ограничивать push веткой, это моё решение.
- Пайплайновый `timeout` не ставил, чтобы время ожидания лида не считалось как время сборки. Таймауты заданы по стадиям.
- Версия библиотеки `v1.4.0`, а не `v1.5.0-rc1`. Имя библиотеки в Jenkins я взял как `depot-pipeline-lib`, по аналогии с коммитом `83c7071`.
- Pre-release-теги в выборе тега образа не участвуют.
- Тег образа с префиксом `v`, как в git.

**Замечания к задаче**
1. В репозитории нет тегов: `список тегов` пуст, в ветке и в истории их нет, remote не настроен. Логика выбора тега не проверена. Если тегов нет, сборка падает с явным сообщением. Тегам нужно быть в репозитории, а Jenkins должен их подтягивать (`git fetch --tags` есть в скрипте).
2. `deploy.sh` нет ни в дереве, ни в истории репозитория. Из задачи не видно, как деплой узнаёт тег образа: в команде его нет. Я экспортирую `IMAGE_TAG` в окружение, но `deploy.sh` должен это читать. Нужно уточнить.
3. Токен передаётся аргументом `--token`, поэтому он виден в `ps` на агенте. Это ограничение самого `deploy.sh` из задачи.
4. Fork-PR: код из форка выполняется на постоянной ноде с доступом к Docker. Чтобы не отдать секреты, в multibranch-job нужны настройки Trust для PR из форков и Jenkinsfile из целевой ветки. Credentials лучше сделать folder-scoped. Это настройки Jenkins, из git я их не проверю.
5. Если нод с меткой `dotnet-linux` больше одной, стадия Push может попасть на другую ноду, где образа нет. Нужно проверить число нод или объединить Image и Push.
6. Подтверждение prod не ограничено по `submitter`. Его стоит ограничить группой лида.
7. В истории есть `Jenkinsfile` из коммита `83c7071` (не в этой ветке). Там ожидание подтверждения идёт внутри агента на 24 часа. При слиянии веток будет конфликт, и новый вариант его заменяет.
8. Для пайплайна нужны плагины: Pipeline, Git, GitHub Branch Source, Credentials Binding, Workspace Cleanup, MSTest. Обновлять все плагины разом не нужно.
9. Не проверено: синтаксис declarative не валидировался (Jenkins и линтер недоступны), пайплайн не запускался. Из `post` верхнего уровня `notifySlack` вызывается без ноды. Если библиотека использует workspace, его нужно перенести в стадию.
10. `depot-worker` по runbook должен быть ровно в одном экземпляре. Деплой-скрипт не должен его масштабировать.
