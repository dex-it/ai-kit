Jenkinsfile добавлен в корень репозитория, в рабочем дереве, без коммита. Синтаксис не проверен: в окружении нет Groovy/Jenkins, доступен только git.

**Изменённые файлы**
- `Jenkinsfile` (новый, 168 строк)

**Что сделано**
- Declarative pipeline, `agent none`, на агентах с меткой `dotnet-linux`. Чекаут явный в каждой стадии.
- Библиотека `depot-pipeline-lib@v1.4.0`, шаг `notifySlack(currentBuild.currentResult)` в `post`.
- Стадии: Build → Test (Unit и Integration параллельно, trx публикуются через `mstest`) → Image → Deploy stage (только `main`) → Approve prod (только `main`, `input` с таймаутом 72 часа, без агента) → Deploy prod (только `main`).
- Тег образа: наибольший semver-тег git + `-${BUILD_NUMBER}`. Сравнение реализовано в Groovy по правилам semver, пре-релизы младше релиза. `git fetch --tags --force` перед выборкой.
- Учётки: `registry-creds` и `deploy-token` подключаются только через `withCredentials` внутри нужных стадий. Логин в реестр идёт во временный `DOCKER_CONFIG`, который удаляется по `trap`.

**Решения, которые стоит проверить**
- **Пуш только из `main`.** Задача этого прямо не требует. Иначе учётка реестра доступна коду из PR, в том числе из форков.
- **Версия библиотеки `v1.4.0`.** Выбрана стабильная; `v1.5.0-rc1` — кандидат. Содержимое библиотеки не проверял.
- **Таймаут ожидания лида — 72 часа.** Подберите по вашей практике.

**Замечания к задаче**
1. **Тегов в репозитории нет.** `список тегов` пуст, в `refs` только ветки. Без тегов стадия Build падает с ошибкой «нет semver-тегов». Нужно проверить, что теги есть на remote и что `fetch --tags` их подтягивает.
2. **`./deploy.sh` в репозитории отсутствует** (`git ls-files` его не содержит), поэтому не проверено, что он делает.
3. **Тег образа deploy.sh не получает.** По описанию он принимает только `--token` и `--env`. Jenkinsfile передаёт тег переменной окружения `IMAGE_TAG` (и `IMAGE` для docker). Нужно убедиться, что deploy.sh берёт её, иначе будет выкатываться не тот образ.
4. **Токен виден в списке процессов.** `deploy.sh` принимает токен аргументом, поэтому он доступен через `ps` на агенте. Безопаснее передавать через stdin или переменную окружения, но это меняет интерфейс deploy.sh. Решение за командой.
5. **Ограничение доступа к `input`.** Кто может подтвердить prod, не задано. Нужна группа лидов в параметре `submitter`.
6. **Пайплайн-`post` с `agent none`.** `notifySlack` в нём должен работать без workspace и агента. Если шаг библиотеки использует `sh` или `env`, его нужно переносить в стадию с агентом.
7. **Зависимости на Jenkins-стороне.** Нужны плагины Pipeline, Git, MSTest (для `mstest`) и Credentials Binding. Integration-тестам нужен Docker на агенте.
8. **Безопасность PR из форков.** Jenkinsfile из PR выполняется на агенте. Нужно настроить trust для форков в multibranch-job, иначе код форка получит доступ к агенту и workspace.
