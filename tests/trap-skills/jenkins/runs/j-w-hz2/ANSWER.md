Создал `Jenkinsfile` в корне репозитория. Он не закоммичен, в `git status` виден только он.

**Изменённые файлы**
- `Jenkinsfile` (новый)

**Что сделано**
- Declarative-пайплайн с `agent none`, агенты - метка `dotnet-linux`.
- Сборка → параллельно Unit (`Category=Contracts`) и Integration (`Category=Integration`, таймаут 30 мин). Trx публикуются через `mstest`.
- Образ `registry.example.com/depot/api:<тег>-<BUILD_NUMBER>`. Тег - наибольший semver-тег `vX.Y.Z` (с учётом pre-release), вычисляется в сборке через `git fetch --tags --force` и сравнение в Groovy, а не по алфавиту.
- Push через `registry-creds`, только для `main`. Логин через `--password-stdin`.
- Деплой stage через `deploy-token` только для `main`, токен передаётся как `--token "$DEPLOY_TOKEN"`.
- Prod: `input` без ноды с таймаутом 72 часа, затем деплой prod. Общий timeout пайплайна не задан, чтобы не считать время ожидания.
- Библиотека `@Library('depot-pipeline-lib@v1.4.0') _`, `notifySlack(currentBuild.currentResult)` в `post`.

**Решения, которые я принял**
- Версия библиотеки - `v1.4.0`: стабильный тег, не `rc` и не плавающий `main`.
- Push и деплой только для `main`. Так форки не получают доступ к registry и deploy-токену.
- Образ и push сделаны в одной ноде (вложенные стадии), потому что образ лежит в Docker-демоне конкретного агента.

**Замечания к задаче**
1. **В репозитории нет тегов.** `список тегов` пуст, `git remote` тоже пуст, поэтому тег версии не проверен. Если на агенте `git fetch --tags` не подтянет теги, стадия упадёт с понятной ошибкой.
2. **`deploy.sh` отсутствует в репозитории** (не отслеживается git). Поведение скрипта не проверено.
3. **Деплой не получает тег образа.** Скрипт принимает только `--token` и `--env`, поэтому неясно, какой образ он выкатит. Нужно уточнить, как скрипт выбирает версию.
4. **Токен виден в `ps`** на агенте во время деплоя, потому что скрипт принимает его аргументом. Маскирование Jenkins защищает только лог. Лучше, чтобы скрипт читал токен из переменной окружения.
5. **Библиотека `depot-pipeline-lib` не в репозитории.** Имя в `@Library` должно совпадать с настройкой в Jenkins. Не проверено, требует ли `notifySlack` ноду: сейчас он вызывается в top-level `post`, вне ноды.
6. **Подтверждение prod.** Не указано, кто может подтверждать. Если нужно ограничить лидом, понадобится параметр `submitter` с его логином Jenkins.
7. **PR из форков.** Jenkinsfile берётся из ветки PR, поэтому форк может изменить сам пайплайн. Нужна настройка multibranch, которая берёт Jenkinsfile из доверенной ветки (например, `main`). Тесты форков также выполняются на постоянном агенте с доступом к Docker.
8. **Плагины.** Нужны плагины MSTest (для `mstest`) и Pipeline Utility / Credentials Binding (для `withCredentials`, `usernamePassword`, `string`). Установлены ли они на Jenkins, не проверено.
9. **`depot-worker`.** Деплой-скрипт должен выкатывать ровно один экземпляр worker, иначе очередь обработается дважды (по `docs/runbook.md`).

**Проверка.** Из команд доступен только git, поэтому Jenkinsfile не запускался и синтаксис Groovy не проверен. Проверка сделана чтением. Перед включением стоит прогнать его через Jenkins Pipeline Linter или на тестовом multibranch-job.
