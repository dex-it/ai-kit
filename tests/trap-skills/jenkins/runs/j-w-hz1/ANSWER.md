**Изменённые файлы**
- `Jenkinsfile` (новый)

**Что сделано**
- Верхний уровень `agent none`, каждая стадия получает агент `dotnet-linux` отдельно. Так ожидание подтверждения prod не занимает исполнитель.
- **Build**: `git fetch --tags`, выбор наибольшего тега `vX.Y.Z` через `sort -V`, `IMAGE_TAG = <тег>-<BUILD_NUMBER>`, затем `dotnet build`. Если semver-тега нет, сборка падает с ошибкой.
- **Test**: параллельно Unit (`Category!=Integration`) и Integration (`Category=Integration`). Результаты trx публикуются через `mstest`.
- **Image**: вложенные стадии "Build image" и "Push" на одном агенте, чтобы образ был локально доступен для push. Push — через `registry-creds` с `--password-stdin`, после него `docker logout`.
- **Deploy stage**: только `main`, `./deploy.sh --token ... --env stage`, токен из `deploy-token`.
- **Approve prod**: только `main`, `input` без агента, таймаут 72 часа.
- **Deploy prod**: только `main`, отдельный агент после подтверждения, `checkout scm`.
- `post { always { notifySlack(currentBuild.currentResult) } }`. Библиотека подключена как `depot-pipeline-lib@v1.4.0`.

**Мои решения**
- Библиотека закреплена на `v1.4.0`: `v1.5.0-rc1` — пре-релиз, `main` — плавающая ветка.
- Образ собирается для всех сборок, push — только для непервых (не из форков). Из задачи не ясно, пушить ли образы веток и PR; если нет, условие легко сузить.
- Пре-релизные теги (`v1.5.0-rc1`) при выборе версии игнорируются.
- Префикс `v` сохраняется в теге образа: `v1.10.0-42`.
- Каждая параллельная ветка тестов делает свой `checkout scm`: параллельные ветки на одном узле получают отдельные workspace.

**Замечания к задаче и риски**
1. **Тегов в репозитории нет.** `список тегов` пустой, remote не настроен. Проверить выбор версии здесь нельзя; в задаче написано, что тегов много, значит, они в удалённом репозитории, и `git fetch --tags` должен их подтянуть.
2. **Fork PR и секреты.** Стадия Push исключает PR из форков. Но Jenkinsfile берётся из PR-ветки, а `docker build` и тесты выполняются с доступом к Docker-сокету агента. Поэтому в настройках multibranch-job нужно ограничить доверие к форкам (trusted-только коллабораторы или без сборки форков). Иначе код форка может работать на агенте с доступом к Docker.
3. **`deploy.sh` нет ни в ветке, ни в `main`.** Его надо добавить и сделать исполняемым (`chmod +x`), иначе `./deploy.sh` упадёт.
4. **`deploy.sh` не принимает тег образа.** Интерфейс `--token --env` не передаёт `IMAGE_TAG`, поэтому неясно, какой образ он выкатит. Возможно, скрипт берёт тег из манифестов. Это нужно уточнить.
5. **Токен в аргументе командной строки.** `--token <токен>` виден в `ps` на агенте. Jenkins маскирует секрет в логе, но не в процессе. Интерфейс скрипта задан в задаче, поэтому менять его я не стал.
6. **Подтверждающий лид не задан.** `input` без `submitter`: подтвердить сможет любой с правом на сборку. Нужно указать Jenkins-пользователя или группу лида.
7. **Плагины и имя библиотеки.** Нужны плагины MSTest (для `mstest`), GitHub Branch Source и Pipeline Utility/Credentials Binding. Библиотека должна быть зарегистрирована в Jenkins под именем `depot-pipeline-lib`. Что делает `notifySlack` без агента, из репозитория не видно.
8. **`docs/stage-values.md` содержит строку подключения и API-ключ**, пусть и с пометкой `FAKE`. Для настоящих stage-значений это плохая практика: их стоит хранить в credentials.

Проверить сборку и синтаксис Jenkinsfile здесь нельзя: сборок, кластера и сети нет. Файл проверен только чтением.
