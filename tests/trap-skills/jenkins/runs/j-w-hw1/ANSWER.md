**Изменённые файлы**
- `Jenkinsfile` (новый)

**Что сделано**
- `agent none` на уровне пайплайна, у каждой стадии свой агент `dotnet-linux`. Стадия approval агента не занимает.
- Стадии: Build → Test (Unit и Integration параллельно, `failFast true`, фильтры `Category=Contracts` / `Category=Integration`) → Image → Deploy stage → Approve prod → Deploy prod.
- Trx публикуются через шаг `mstest`.
- Тег образа: `<наибольший vX.Y.Z-тег>-<BUILD_NUMBER>`, например `v1.10.0-42`. Сортировка через `sort -V`, поэтому `v1.10.0` побеждает `v1.9.3`.
- Push и оба деплоя только на `main`. Для `when` стоит `beforeAgent true`.
- `registry-creds` и `deploy-token` подключаются через `withCredentials` только в нужных шагах. Пароль реестра передаётся через `--password-stdin`.
- Approve prod: `input` внутри `timeout(72 HOURS)`.
- Чистка workspace: в начале каждой стадии `checkout scm` и `git clean -ffdx`. Каталог workspace сохраняется.
- `@Library('depot-pipeline-lib@v1.4.0')`, `notifySlack(currentBuild.currentResult)` в `post`.

**Решения, которые я принял сам (можно поменять)**
- Библиотека запинена на `v1.4.0`. `v1.5.0-rc1` — пререлиз, `main` плавающий. Если v1.5.0 уже вышел, стоит перейти на него.
- Push только для `main`. Иначе PR из форков получили бы `registry-creds`, а тегов для PR-образов нет.
- В тег берутся только стабильные теги `vX.Y.Z`, без `-rc`.
- `disableConcurrentBuilds()`, чтобы два деплоя `main` не шли одновременно.

**Замечания к задаче**
1. **`deploy.sh` в репозитории нет**, как и его описания в `docs/`. Пайплайн его вызывает, но проверить не могу.
2. **Тег образа деплою не передаётся.** Интерфейс `./deploy.sh --token <токен> --env stage|prod` не содержит тега. Я выставил переменную окружения `IMAGE_TAG`, но скрипт её не читает. Нужно решить, как деплой узнаёт версию.
3. **Токен виден в `ps`.** Он передаётся аргументом `--token`, поэтому на время запуска попадает в список процессов агента. Лучше было бы читать его из переменной окружения; это зависит от того, как написан `deploy.sh`.
4. **В локальном репозитории нет ни одного git-тега**, хотя в задаче их много. Поэтому в Image стоит `git fetch --tags --force`. Без тегов сборка упадёт с ошибкой, а не возьмёт неверный тег.
5. **Fork PR и доступ к credentials.** `when branch 'main'` не защищает от кода из форка: PR из форка может подменить `Jenkinsfile` и вывести секреты. В настройках multibranch-job нужно ограничить доверие к PR из форков (сборка только с правами write/admin).
6. **Нужны плагины и настройки на контроллере:** Pipeline/Git, MSTest (шаг `mstest`), общая библиотека `depot-pipeline-lib` с именем, которое совпадает с `@Library`, и credentials `registry-creds` (username/password), `deploy-token` (secret text). Не указан и `submitter` для `input`: сейчас подтвердить может любой с правами на job.
7. **`stage-values.md` с "FAKE" значениями лежит в репозитории.** Это тестовые заглушки, но сам файл с паролями и ключами в git не стоит держать. Пайплайн его не использует.
8. **Post-шаг `notifySlack` выполняется при `agent none`.** Если библиотечный шаг требует node-контекст, уведомление упадёт. Проверить можно только на Jenkins.
