Я добавил `Jenkinsfile` (declarative) в корень репозитория. Это единственный изменённый файл, коммита нет. Запустить и проверить пайплайн было нечем: сборок и сети нет, из команд работает только git.

**Как устроен пайплайн**
- **Агент:** метка `dotnet-linux`. Перед сборкой стоит `cleanWs()`, потому что workspace на нодах сохраняется между сборками. Кэш NuGet лежит в workspace.
- **Стадии:** Checkout, Build, Test (Unit и Integration параллельно), Image, Push, Deploy stage, Approve prod, Deploy prod.
- **Тесты:** unit запускается с фильтром `Category!=Integration`, integration с `Category=Integration`. У каждого свой каталог результатов. trx публикуются плагином xunit (`MSTest(...)`).
- **Тег образа:** берётся наибольший тег `vX.Y.Z` по `--sort=-v:refname`, и к нему добавляется номер сборки, например `v1.10.0-42`. Для этого checkout делается с тегами и без shallow. Пререлизные теги не учитываются. Если подходящих тегов нет, сборка падает.
- **Библиотека:** `@Library('depot-pipeline-lib@v1.4.0')`. Я закрепил релизный тег, а не `v1.5.0-rc1` или `main`. `notifySlack` вызывается в `post` для SUCCESS, UNSTABLE, FAILURE и ABORTED.
- **Подтверждение на prod:** стадия `input` идёт с `agent none` и таймаутом 3 дня, поэтому executor на время ожидания не занят. Деплой на prod берёт новую ноду и заново делает checkout.
- **Секреты:** `registry-creds` передаётся через `docker login --password-stdin`. `DOCKER_CONFIG` свой на каждую сборку, и после push выполняется `logout`. Токен деплоя `deploy-token` подставляет shell из переменной окружения, а не Groovy. Образ после сборки удаляется с ноды.

**Замечания к задаче**
1. В задаче не сказано, пушить ли образы из веток и PR. Я пушу и деплою только с `main` и не из PR. Из PR, особенно из форков, секреты не должны быть доступны. Если нужен push из веток, поправьте условие `when` на стадии Push.
2. `./deploy.sh` принимает токен аргументом, поэтому его видно в `ps` на общей постоянной ноде. Лучше, чтобы скрипт читал токен из переменной окружения или из stdin.
3. Для fork PR в multibranch-job нужна доверительная политика, при которой Jenkinsfile берётся из целевой ветки (Trusted). Иначе форк может подменить пайплайн. Это настраивается в job, не в файле.
4. Нужны плагины Workspace Cleanup и xunit. У плагина xunit в этом пайплайне лучше проверить поддержку trx.
5. Я предполагаю, что `notifySlack` работает без `node`: он вызывается из `post` на уровне пайплайна, где агента нет. Если шагу нужен workspace, оберните вызов в `node`.
6. Таймаут подтверждения (3 дня) выбран мной. Ограничения по `submitter` для лида тоже нет, потому что логин или группа лида неизвестны. Их стоит добавить в `input`.
7. `disableConcurrentBuilds()` стоит на всём job, и сборка, которая ждёт подтверждения prod, блокирует следующие сборки той же ветки. Если это мешает, добавьте `abortPrevious` или уберите опцию.
