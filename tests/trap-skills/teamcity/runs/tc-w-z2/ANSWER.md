Я добавил конфигурацию TeamCity как код, но не проверял её: сборки и сети нет, поэтому Kotlin DSL ни разу не компилировался. Ничего не закоммичено.

**Созданные файлы** (все новые, в `.teamcity/`):
- `settings.kts` — проект `Depot` с версией 2024.12. Он только вызывает `dotnetServicePipeline(ServiceSpec(...))`.
- `DotnetServicePipeline.kt` — общая схема цепочки. Остальным девяти сервисам нужно только свой `ServiceSpec`.
- `pom.xml` — нужен TeamCity для компиляции Kotlin DSL.

**Что в цепочке**
- **Цепочка:** Build, затем unit (`Category=Contracts`) и integration (`Category=Integration`) тесты. Дальше образ с push, деплой на stage и деплой на prod. Prod запускается только кнопкой Run, без триггеров.
- **Деплой:** образ собирается из `Dockerfile` (там же `dotnet publish`) и пушится. Шаг образа пишет `deploy-values.yaml` с тегом и digest и публикует его как артефакт. Оба деплоя берут этот артефакт из того же билда образа через snapshot-зависимость.
- **Триггеры:** деплой на stage запускается по VCS на `main` и тянет за собой всю цепочку. PR, в том числе из форков, собираются только до unit-тестов.
- **Секреты:** `db.password`, `registry.password` и `deploy.token` — параметры типа password. Они попадают в шаги через переменные окружения, а не через командную строку. Значения нужно задать в UI или в хранилище.
- **Защита от прошлых инцидентов:** unit и integration падают, если число тестов меньше 1. Они также падают, если в логе есть `System.OutOfMemoryException`, `The active test run was aborted` или `No test matches the given testcase filter`.

**Замечания к задаче**
1. **Механизм деплоя не описан, и манифестов в этой ветке нет.** Они есть только в `feature/k8s-deploy`. Я предположил `helm upgrade` с токеном в `HELM_KUBETOKEN` и значениями из `deploy-values.yaml`. Параметр `deployChart = "deploy/depot"` — заглушка (TODO). Если деплой другой, нужно поправить шаг.
2. **Заглушки:** URL репозитория (`https://git.example.com/...`) и тип хостинга. Для PR из форков я взял GitHub. В `pom.xml` остался плейсхолдер `%TEAMCITY_SERVER_HOST%`, его надо заменить на адрес сервера.
3. **Параметры сверх списка из задачи:** `vcs.user`, `vcs.password`, `registry.host`, `registry.user`. Их нужно завести.
4. **Fork-PR и секреты.** Безопасность держится на том, что PR-цепочка состоит из Build и unit, где секретов нет. Но параметры `db.password` и остальные заведены на уровне проекта, поэтому любой, кто может вручную запустить integration или деплой на ветке PR, получит секреты. Запретить такие запуски нужно правами ролей в TeamCity.
5. **Один токен на два окружения.** `deploy.token` общий для stage и prod. Лучше завести отдельный токен для prod.
6. **Заглушка в тестах.** Integration-тест в `StockTests.cs` пустой (`Assert.Equal(OK, OK)`). Он зелёный, но ничего не проверяет. `db.password` тест не читает: Testcontainers сам поднимает Postgres. Параметр передаётся на будущее.
7. **Переиспользование на девяти сервисах.** Сейчас `DotnetServicePipeline.kt` лежит в репозитории Depot. Чтобы сервисы не копировали файл, его стоит вынести в общий репозиторий или в DSL-библиотеку и подключить как зависимость в `pom.xml`.
8. **Версия .NET SDK.** `global.json` требует 8.0.100 с `rollForward: latestFeature`, а `Dockerfile` использует 8.0.404. На агентах должен стоять SDK 8.0.x.
