## Тип единиц и дубли (шаг 0)

Содержание - конвенции корпуса требований (что пишется в журнал, как на запись ссылаются, как
оформляется пересмотр) плюс процедура владельца журнала. Конвенции видны из соседних файлов корпуса,
поэтому мерятся кейсами на корпусе, где они уже соблюдаются, а не остаются процедурой без свидетельства;
решение в пользу кейсов принято до прогонов. Процедура владельца (кто заводит, развилка
«есть / утрачен / нет / корпуса нет», кто дописывает, черта ревизии) - база process-skill: её
потребители - команды, которые `dex-skill-node-contract` не грузят, поэтому дубль с ним
(`references/decision-log-ownership.md`) не снимается, дом для команд - здесь.

Дубли:
- «Род изменения не записан» = `unit-identity` «Правку вносят молча, род изменения не объявляют»: дом -
  `unit-identity` (на него ссылаются `node-contract` `references/revision.md` и `domain-analyst`), здесь
  остаётся запись рода в журнале.
- «Правка пришла мимо конвейера» - единица о `quality-checks`, дом здесь.

## Кейсы

Девять кейсов - поручения аналитику, ведущему требования (поручения дословно - массив `T` в раннере).
K0 - «сколько живут баллы и почему» (ничего не менять); K1 - решение «12 месяцев» поверх D-3; K2 -
ограничение с неизвестной долей; K3 - правило, уже стоящее как `FR-2002`; K4 - мера на API, уже
покрытая `NFR-1002` фичи 01; K5 - снятие баллов за отзывы; K6 - решение для фичи 03 с утраченным
журналом; N1 - новая фича в Loyalty; N2 - новая фича в Wallet. Коды в `runs/`: `<кейс>-c<N>` - контроль
без скилла, `<кейс>-n<N>` - редакция n1, `<кейс>-r<N>` - ревизия n2 (K0, K2, K4), `<кейс>-f<N>` - итоговая
2.0.0 (n2 плюс рез по `norm-writing`: сняты действия чужой роли - узла, не владельца журнала). В каталоге прогона - `DIFF.patch`
рабочего дерева и `ANSWER.md`.

## Открыто

- L8, L10, L17 - `unverifiable`: гейт между судьёй и владельцем, параллельные узлы с одним журналом и
  свёртка контекста кейсом одного исполнителя не вынуждаются. Остаются фразами в процедуре.
- L14 (правка мимо конвейера): кейс не построен - нужен корпус, где текст единицы разошёлся с ревизией
  в `quality-checks`. Остаётся фразой.
- K6 (n1): по процедуре файл поверх утраты не заводится, и оба прогона вписали новое число в `FR-3002`
  без записи - решение лежит только в ответе владельцу. Ключ это принимает (утрата названа, основание -
  «поднять заново»); в 2.0.0 это разведено явно (пункт ниже).
- L16 в контроле: ключ K6 требует назвать утрату и не воссоздавать записи; занятие утраченного номера
  новым решением ключ не называл, засчитано провалом L16 по тексту единицы 1.6.1 («номера утраченных
  записей не переиспользуются»). Ключ проекта не расширялся - расширение после прогонов контроля было
  бы подгонкой; единица возвращена фразой, n1 и 2.0.0 номер не заняли (4/4).
- K6 (2.0.0): «Утрата» разведена с «сначала запись»: новое решение по утраченному журналу идёт
  списком в выходе, основание единицы - «запись - поднять заново». Правка после прогона f по находке
  саморевью, перепрогон не делался - поведение k6-f1/f2 (решение в ответе владельцу, файла нет)
  правке соответствует.
- K6 контроль c1 завёл журнал фичи 03 с новой записью D-4 и назвал D-1..D-3 утраченными: по ключу
  верно, по процедуре владельца (файл не заводится) - нет. Судилось по ключу.
- K4 (2.0.0, k4-f1): завёл `NFR-2002` (300 мс) рядом с `NFR-1002` (500 мс) вместе с открытым пунктом
  «возможный дубль» и вопросом владельцу - ключ это допускает; k4-f2 и все прогоны n1 и n2 меры не
  заводили, только пункт.
