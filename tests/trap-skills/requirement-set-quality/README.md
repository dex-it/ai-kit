# requirement-set-quality: сжатие по свидетельству, группа 3.1

Скилл `dex-skill-requirement-set-quality` 1.7.0 ([`inputs/SKILL-1.7.0.md`](inputs/SKILL-1.7.0.md)), эпик
#291, группа 3.1 (#300). Итог - 2.0.0, process-skill ([`inputs/SKILL-2.0.0.md`](inputs/SKILL-2.0.0.md);
промежуточная n1 - [`inputs/SKILL-n1.md`](inputs/SKILL-n1.md); текст PR до ревью - [`inputs/SKILL-9c3f7de7.md`](inputs/SKILL-9c3f7de7.md);

[`tests/README.md`](../../README.md).

Вход, среда, раннер, наборы прогонов и судьи - общие для группы, описаны в протоколе
[requirement-quality](../requirement-quality/README.md); прогоны и файлы вердикта лежат там же. Скилл
мерится кейсами r2 (ревью набора, `badset`), r5 (готовность, `ready`) и c0 («ничего не менять»).

## Потребители

`requirements-reviewer` (Set Analysis), `implementer-reader` (раздел «Готовность набора» по имени);
скиллы `design-quality`, `plan-quality`; `business-requirements-analyst` и `domain-analyst` называют
его, чтобы не грузить. Бандлы `product-manager`, `system-analyst`. Кейс активации
`requirement-set-quality-in`.

Входящие ссылки по имени раздела: «Готовность набора» (`implementer-reader`) - в 2.0.0 есть.

## Тип единиц (шаг 0)

20 H3-ловушек в семи разделах по характеристикам набора INCOSE C10-C14. Вводная (вход оракула, кто его
грузит, запись `unverifiable` без узла-судьи) и «Готовность набора» (порог, чистый контекст пробы) -
процедура оракула и контракт `implementer-reader`: остаются фразами. «Пара с общим предметом сливается
вместо находки» - дом `unit-identity`, снята дублем.

## Открыто

- «Сроки» в r2 со скиллом ниже контроля. Контроль 3/4 (добор `c3`, `c4` - [`JUDGE-i.md`](../requirement-quality/JUDGE-i.md))
  называет раздел планом не на месте; `s` и `v` 0/4 судят его по выполнимости (триада «Выполнимость по
  сумме»). Триада снята: `f` 1/4 (`f1` - источник даты, `f2` да, `f3` не упомянут, `f4` - источник и
  выполнимость); по правилу, записанному до добора контроля, итоговая не хуже, если её взятия >= взятий
  контроля минус 1, - 1 < 2, хуже. Проверенные ступени (каждая записью до прогонов, r2 и c0 по 2):
  - `h` - ось Feasible снята из строки осей: «Сроки» 1/2, FR-2012 и FR-2020 ниже `f`, c0 2/2 - не держит
    ([`JUDGE-h.md`](../requirement-quality/JUDGE-h.md));
  - `j` - название «Раздел набора - не требование к системе (план работ, сроки, ресурсы)»: «Сроки» 2/2, c0 2/2,
    но FR-2012 0/2 и FR-2020 0/2 (у `f` да 2/2) - по правилу записи вред, не держит
    ([`JUDGE-j.md`](../requirement-quality/JUDGE-j.md)).
  Текст остался `f`. Наблюдение: просадка FR-2012 и FR-2020 повторилась в `h` и `j`, и у обоих
  `requirement-quality` - итоговая `g`, у `f` - редакция `f`; FR-2012 у `j` - тот же якорь («когда не хватает
  часов пакета»), который судья контроля засчитал «да» (`JUDGE-control.md`, c2). Причина - редакция
  `requirement-quality`, правка `requirement-set-quality` или калибровка - не различена. Различает её r2 по 2 на
  текстах `f` с `requirement-quality` `g`; прогона нет. Решение за владельцем: принять `j` (польза на «Сроках»
  2/2 против `f` 1/4) с открытым FR-2012/FR-2020 либо ставить различающий прогон.
- «Мера успеха односторонняя»: засев FR-2020 негоден - вторую сторону меры даёт соседний FR-2019, и
  находка `v` «иначе» это и показывает. Триада восстановлена дословно из 1.7.0 до кейса, где вторая
  сторона не наблюдаема нигде в наборе; на восстановленном тексте `f` 2/2 («мера односторонняя»).
- «Правило без данных», «Нет способа валидации»: засевов в наборе нет; оставлены как написаны.
- FR-2006 против NFR-0001: `s` и `v` 1/2, `f` 2/2 судят то же правило против ADR-001 (контроль - тоже через
  ADR-001, засчитан); FR-2012 - у `s`, `v`, `f` та же догадка «имелся в виду пакет», что у контроля. Отдельного
  перепрогона под эти пункты нет.
