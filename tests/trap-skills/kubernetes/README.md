## Ревизия 3 по ревью владельца (PR #368): K4

Тело скилла не менялось. Ключ K4 (`_projects/depot/README.md`) требовал `requests` и `limits` по памяти и CPU; документация
Kubernetes (Resource Management for Pods and Containers, раздел о requests и limits) CPU limit обязательным не называет: он работает
через throttling, и его часто опускают. Требование CPU limit в ключе - сверх нормы. Вердикт по ключу как записан (до прогонов): K4 в `k-w` 0/2. Пересчёт c1, c2 по ключу, поправленному после прогона, - наблюдение, снятием не засчитывается до решения владельца; снятие K4 - прогоном по ключу, записанному до него (стек #376). Пункт «без requests и limits» остаётся в теле как признак (по замечанию владельца пункт не трогаем). Пересчёт построен на ответе без перепрогона: основание - правка ключа вниз, а не новая оценка исполнителя; после просмотра ответов правило 3 набора такое чтение не принимает.

## Ревизия 4 (стек на #368): K4 снят

Основание - метод, не вкус: единица остаётся, только если без неё исполнитель ошибается. После ревизии 3 ключ K4 требует `requests` (память и CPU) и memory limit, CPU limit не требует; контроль `c1`, `c2` в `k-w` это выполнил 2/2, в `k-f` K4 2/2. Единица снимается контролем (шаг 2 метода); пункт «requests и limits» держался только решением «не трогаем» (ревизия 3), снят в этом стеке. Правило набора и редакция 1.3.0 (K1, K7) закоммичены до прогонов (`454b097d`, поправка текста ключа K4 в `_projects/depot/README.md` - документирует ревизию 3, не новую оценку).

Правка после ревью (mmx003, стек на #368), прогоны не перегенерированы, ключ не менялся: (1) раннер `run-group-4-4.sh:36` пишет `git add -A -N . && git diff -- .`; против индекса `git diff` не показывает удаление отслеженного файла (зонд на пустом репозитории: `git diff` без удаления, `git diff HEAD` с ним), поэтому `secret.yaml` удалён в `ANSWER.md:18`, но не в `DIFF.patch` (0 вхождений в `k-f-i1`, `k-f-i2`); по правилу 2 набора слова без правки файла не засчитываются, клетка K7 в `k-f` здесь держится на ответе, как и в `k-f` 1.2.0 (`f`). K7 в `k-w` 2/2 по файлам. (2) K5 по ключу требует CPU limit не меньше 300m у API; в `k-w-i1`, `k-w-i2` CPU limit не задан (как и в контроле `c1`), поэтому клетка K5 по CPU - н/д, по памяти - да. (3) `n-ci`, `k-t`: н/д - снятие пункта сужает подачу, предмет этих кейсов (K11, приманки `n-ci`) пунктом K4 не задет; `n-ci` кормится дисциплиной `ci-gates` (дом кейса), в шести прогонах `n-ci` (`c`, `f`, `g`) слов requests и limits нет, клетки N и B-N от K4 не зависят; `k-t` судит K11 (`--previous`), пункта K4 в нём нет.

K4 без пункта в скилле 2/2 в обоих кейсах - то же, что в контроле. K1 в `k-w` 2/2 и `k-f` 2/2 (в 1.2.0 `f` тоже 2/2), K7 в `k-w` 2/2 по файлам и `k-f` 2/2 по ответу (`DIFF.patch` удалений не несёт, см. правку после ревью; в контроле 0/4; в `i` исполнитель не создаёт `Secret` со значениями и называет вынос секрета в ответе - как в 1.2.0, `f`). Оценка не хуже 1.2.0 и контроля. Оговорка: выборка 2 на кейс, K7 в `k-w` в контроле 0/2 держится на тексте пункта K7, при другой формулировке задания вердикт не переносится.
