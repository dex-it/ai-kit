## Ревизия 3 по ревью владельца (PR #368): K4

Тело скилла не менялось. Ключ K4 (`_projects/depot/README.md`) требовал `requests` и `limits` по памяти и CPU; документация
Kubernetes (Resource Management for Pods and Containers, раздел о requests и limits) CPU limit обязательным не называет: он работает
через throttling, и его часто опускают. Требование CPU limit в ключе - сверх нормы. Вердикт K4 считается без него: `k-w` c1 и c2 задали
`requests` и memory limit, то есть признак «без requests и limits» они не нарушили; K4 в `k-w` контроля - не 0/2, а 2/2, по методу
такая единица была бы снята контролем. Пункт «без requests и limits» остаётся в теле как признак (по замечанию владельца пункт не трогаем);
снимать ли его - решение владельца эпика, вопрос в «Открыто» группы. Пересчёт построен на ответе без перепрогона: основание - правка ключа
вниз, а не новая оценка исполнителя.

## Ревизия 4 (стек на #368): K4 снят

Основание - метод, не вкус: единица остаётся, только если без неё исполнитель ошибается. После ревизии 3 ключ K4 требует `requests` (память и CPU) и memory limit, CPU limit не требует; контроль `c1`, `c2` в `k-w` это выполнил 2/2, в `k-f` K4 2/2. Единица снимается контролем (шаг 2 метода); пункт «requests и limits» держался только решением «не трогаем» (ревизия 3), владелец принимает или отклоняет снятие этим стек-PR. Правило набора и редакция 1.3.0 (K1, K7) закоммичены до прогонов (`454b097d`, поправка текста ключа K4 в `_projects/depot/README.md` - документирует ревизию 3, не новую оценку).

Перепрогон на редакции 1.3.0 (набор `i`, раннер `run-group-4-4.sh` дословно, `claude-sonnet-5-5` medium, CLI 2.1.304 - на патч-версию новее прогонов 2.1.303, `skills=[]`, `mcp=[]`, `esc=[]`), по 2 прогона на `k-w` и `k-f`, $0.54:

| Кейс | K4 (requests, memory limit) | K1 | K7 | Остальное |
|---|---|---|---|---|
| `k-w-i1` | requests cpu и memory, memory limit у API и worker - да | liveness `tcpSocket`, readiness `/health` - да | значений в репозитории нет, Secret создаётся вручную - да | K2, K3, K5, K6, K8, K10 - да |
| `k-w-i2` | да | да (`tcpSocket`) | да | K2, K3, K5, K6, K8, K10 - да |
| `k-f-i1` | requests и limits (cpu, memory) - да | liveness `tcpSocket`, readiness `/health` - да | `secret.yaml` удалён, назван в ответе - да | worker не тронут |
| `k-f-i2` | да | да | да, назван в ответе | worker не тронут |

K4 без пункта в скилле 2/2 в обоих кейсах - то же, что в контроле. K1 в `k-w` 2/2 и `k-f` 2/2 (в 1.2.0 `f` тоже 2/2), K7 в `k-w` 2/2 и `k-f` 2/2 (в контроле 0/4; в `i` исполнитель не создаёт `Secret` со значениями и называет вынос секрета в ответе - как в 1.2.0, `f`). Оценка не хуже 1.2.0 и контроля. Оговорка: выборка 2 на кейс, K7 в `k-w` в контроле 0/2 держится на тексте пункта K7, при другой формулировке задания вердикт не переносится. Проба активации по полю 1.3.0: `kubernetes-in` 3/3 (запрос переписан: «лимитов не выставляли» в нём подводило под снятый пункт, теперь про перезапуск при недоступной БД), `kubernetes-near` 3/3 не активирует ($0.36).

Альтернатива (отклонение стека): исходный PR остаётся рабочим, K4 живёт названием «Контейнер без requests и limits» в 1.2.0. Цена такого пункта: около 35 символов в каждой загрузке скилла ради ситуации, которую исполнитель без скилла не нарушает.
