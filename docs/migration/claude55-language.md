### Решение и протокол (ворота ◆4, по размеру)

Протокол зафиксирован до прогонов:

1. Размер единицы или итога выборки = байты UTF-8 (знаки и слова - справочно). Допуск роста - ноль.
2. Качество: доля удержанных ограничений по единице (прокси E5/E11), разброс = стандартное отклонение доли между повторами, ошибки трактовки = число вопросов с ответом против эталона. «Не хуже» - разность «после» минус «до» не ниже минус полосы шума тира (Haiku 0,11, Sonnet 0,14 по E10; для Opus полосы нет, берётся 0,14 как верхняя оценка).
3. Принимается только то, что не выросло по размеру и не хуже по качеству. Рост без значимого выигрыша - «не принято» с протоколом. Принятое - нормой письма в `optimize-for-llm` или `norm-writing`, строкой взамен названной снимаемой, после прогона набора `tests/optimize-for-llm` (правило смены скилла, предмет которого - поведение исполнителя).

Исход:

| Предмет | Размер | Решение |
|---|---|---|
| Пакет R1-R7 (все восемь единиц) | +514 байт (+7,3%), слов +9,0%, предложений 31 -> 54 | **не принято**: размер вырос, выигрыш не заявлен и не измерен; серия не запускается |
| R6 (длина предложения, T = 29) | 0 байт | размер допускает; качество не измерено -> **ждёт серии** |
| R2, R4 | - | совпадают с действующими нормами, отдельного решения не нужно |
| R1, R3, R5, R7 порознь | не мерены | не принято вместе с пакетом; отдельная проверка только по просьбе владельца |

Оговорки: выборка из восьми единиц, один переписчик; рост может быть меньше на единицах, где исходник уже написан полными предложениями (u4: +1,0%), и больше на эллипсисах (u5: +25,0%). Вывод «правила удлиняют текст» подтверждён на этой выборке, на каталоге в целом - нет.

5. Причина группы не выводится за один проход -> вызов `Agent` с `subagent_type` полной формой (`dex-debugger:debugger`), не голое имя.
6. Один вызов дебаггера на группу независимо от числа симптомов.
7. Группа уходит в Phase 3 только с `accepted`, `harness-fixed` или `n/a`.
8. Confidence ниже 80 -> clarify, кодом догадка не закрывается.
9. Соседнее «заодно» не чинится, уходит в открытые наблюдения.
10. Проба переходит из red в green без изменения самой пробы.
11. Недоделок в diff нет (TODO без тикета, заглушка, проглоченная ошибка, debug-вывод).
12. Статус техутверждений причины - `verified`, `unverifiable` или `contradicted`.

**`business-requirements-analyst`**

1. В BRD нет `UC-NNN` и сценариев с ходом и расширениями.
2. Нет `FR` и `NFR`; у требования нет метода верификации и числа вместо MOE.
3. Путь артефакта: сквозное поле берётся как есть; иначе `project-docs-map`; записать некуда -> `status: blocked` с названной ступенью.
4. Номер `BR-NNN`: инкремент ключа `NN.BR` в `.req_counter`; при `level: product` - без старшего разряда, номер фичи не запрашивается.
5. Пустой вход (ни идеи, ни брифа, ни кода) -> `status: blocked`; сырая идея `blocked` не даёт.
6. `mode` по умолчанию `autonomous`: бизнес-вопрос решается вопросом-с-предложением и записывается в открытые вопросы, без остановки; `interactive` возвращает вопрос сразу.
7. Вопрос автору имеет форму «принял X, потому что Y; подтверди или поправь».
8. Раздел рисков обязателен (probability, impact, mitigation).
9. `self-check` - поле выхода; записей в `quality-checks` автор не ставит.
10. `requirement-set-quality` не грузится; в выходе строка «слой набора не прогнан: узла, видящего набор, в вызове нет».
11. `requirement-quality` прогоняется по каждому `BR`; дефект устраняется до выдачи BRD.
12. Статус документа не выше `review` без записей судьи.
13. Приоритет `BR` молча не назначается.
14. Код не открывается (исключение - вход «код без постановки», пометка «реконструировано, не согласовано»).

**`requirement-quality`**

1. Желательность фичи по сути не судится.
2. Дефект единицы - находка `requirement-defect`, адресованная постановщику.
3. Код под дефектный текст не правится.
4. Метода проверки нет -> вердикт единицы `unverifiable`.
5. Противоречие единиц: обе стороны якорями и что требует каждая; сторона не выбирается.
6. Метод проверки, не наблюдающий результат требования, - находка.

**`kafka`**

1. Продьюсер без идемпотентности: повторы дублируют и переупорядочивают сообщения.
2. Накопленные несохранённые смещения читаются заново при ребалансе.
3. Ядовитое сообщение: ограниченное число попыток, затем разбор (топик `*.DLT` или иное хранилище) с содержимым и причиной, смещение движется дальше; повтор на месте без предела партицию не освобождает.

**`root-cause-analysis`**

1. Цепочка от симптома назад до места, где плохое значение возникает впервые.
2. Звено с уликой (`file:line`, лог, метрика, sha).
3. Причина объясняет и затронутое (`IS`), и незатронутое (`IS-NOT`).
4. Проба красная до фикса и зелёная после.
5. Отчёт: цепочка с уликами, причина, фикс, проба до и после.

### Приложение A. Тексты «после» (выборка #38)

**u1**

> **2. Проверяемость каждого требования.** Проверь по каждому требованию: названы ли метод верификации и предмет проверки, а у количественного требования - условия измерения. Формулировка, для которой нельзя назвать способ проверки, не является требованием. Верни такую формулировку в переформулировку либо подними наверх как нехватку воли постановщика. Отдельным проходом проверь атрибуты качества: слово («быстро», «надёжно», «удобно») без наблюдаемого признака проходит проверку заполненности, но не проходит проверку проверяемости.

**u2**

> **Метод верификации обязателен: это сужение сверх стандарта, и каталог называет его сужением.** Требование без метода - декларация, потому что «проверяемое» ничем не подтверждено. **Одного метода не всегда достаточно.** Полная верификация части требований требует более одного метода. Запиши все применяемые методы и не выбирай один ради формы.

**u3**

> Правильно: сделай у меры, задающей состав или количество, обе границы наблюдаемыми - избыток и нехватку. Либо назови источник второй границы (сам состав как закрытый перечень + проверка на его полноту). Принимай одностороннюю меру только с записью: другой механизм ловит противоположное отклонение. Назови этот механизм в записи.
>
> Почему: мера молча пропускает неполноту, и потребитель получает её уже как факт. Мера штрафует избыток, а нехватка не оставляет следа, поэтому набор годами выглядит проверенным.

**u4**

> Не выводи готовность набора из пройденных проверок. Читай набор так, как читал бы автор кода. Выпиши каждое решение о наблюдаемом исходе, мере или границе, которое автору кода пришлось бы принять самому. Порог качественный: список пуст и открытых пунктов нет. Доля покрытия и число открытых пунктов - наблюдение за ходом, а не условие допуска. Строки списка - дефекты набора.

**u5**

> Носитель после правки не больше носителя до правки. Переписывание и сжатие меняют слова, а не состав утверждений. Квантор, условие и выводимое из соседнего утверждение остаются. Если носитель вырос, назови в отчёте единицу, снятую или сжатую взамен. Если снять нечего, поставь `budget-exceeded`. Назови в отчёте выросшую единицу, обязательство, которым закрыт рост, и причину, по которой короче не выражается. Если нет ни единицы взамен, ни `budget-exceeded`, правка не принята.

**u6**

> Замени текст чужой нормы предписанием открыть её дом: вызов `Skill` полной формой `{plugin}:{skill}`, свой `references/` либо скилл из `skills:`. Если текст расходится с домом, запиши расхождение находкой в отчёт. Копию всё равно сними. Если дома нет, оставь норму здесь полной единицей. Запиши недостижимость дома находкой в отчёт.

**u7**

> **Делегирование причины.** Если причина группы не выводится из улик пачки за один проход, спавни `dex-debugger:debugger` через `Agent`. Передай `subagent_type` полной формой: голое имя не резолвится. Делай один вызов на группу независимо от числа её симптомов. Передай дебаггеру симптом, ожидаемое, scope и свой `mode` (планка наследуется вниз). Если причина выводится (стек-трейс указывает на строку; источник совпал с подтверждённым в другой группе), веди группу сам и назови признак строкой в выходе фазы. Считай вернувшиеся причину и тест claim и прими их по `node-contract`, `references/diagnosis-acceptance.md`, обеими сторонами приёмки: ты и правящий, и вызывающий дебаггера. Отправляй группу в Phase 3 только с `accepted`, `harness-fixed` или `n/a`. Если приёмка спорна, вызови дебаггера повторно по разделу «Вызывающий». Исход пунктов 2-3 этого раздела и диагноз без причины - откладывание (Phase 6), включая судьбу теста.

**u8**

> **Gate (делай):** начинай правки рабочего дерева только после команды `делай`, поданной поверх плана, показанного по `оформляй`. До этой команды не меняй ни код, ни ветки, ни стенд. Команды `оформляй` и `делай` - канальный механизм. Если тебя спавнит узел, план не показывается и не ждёт команды, и правки идут сразу. Правка рабочего дерева и локальные коммиты - работа узла, а не outward-facing действие. Санкция на эту работу - сам факт вызова с подтверждённой причиной и планом. Гейт Phase 2 и 4 в этом режиме действует, запрет на push тоже: оба остаются в обоих режимах. Санкция вызова НЕ покрывает мутирующее действие на общем стенде. Перед каждым таким действием запроси отдельное подтверждение (см. ниже и Boundaries). Без канала предложи действие в Output и не выполняй его.

### Приложение B. Скрипты замера (бесплатные, без модели)

`stat.mjs` (считает показатели единицы; `node stat.mjs файл 29`) и `dist.mjs` (распределение по каталогу; `node dist.mjs <корень репозитория>`), лежат рядом при запуске.

```js
// stat.mjs
import { readFileSync } from 'node:fs';
export function split(text) {
  const t = text.replace(/\*\*/g, '').replace(/\n+/g, ' ').replace(/\s+/g, ' ').trim();
  const abbr = /(?:\b\d+|т\.е|т\.д|т\.п|напр|см|п|пп|ср|др|e\.g|i\.e|vs|ID|N)\.$/i;
  const out = []; let cur = '';
  for (const p of t.split(/(?<=[.!?])\s+(?=[А-ЯЁA-Z«`"(\d*])/)) {
    cur = cur ? cur + ' ' + p : p;
    if (abbr.test(cur)) continue;
    out.push(cur); cur = '';
  }
  if (cur) out.push(cur);
  return out;
}
export const words = (s) => s.split(/\s+/).filter((w) => /[\p{L}\p{N}]/u.test(w));
export function stat(text, thr) {
  const lens = split(text).map((s) => words(s).length);
  const sum = lens.reduce((a, b) => a + b, 0);
  return { bytes: Buffer.byteLength(text), chars: [...text].length, words: sum, sentences: lens.length,
    mean: +(sum / lens.length).toFixed(1), max: Math.max(...lens), long: lens.filter((l) => l > thr).length };
}
if ((process.argv[1] || '').endsWith('stat.mjs') && process.argv[2])
  console.log(JSON.stringify(stat(readFileSync(process.argv[2], 'utf8'), Number(process.argv[3]) || 29)));
```

### Приложение D. Образцы перевода (#39)

**p1**

RU: Фича в основной ветке, с неё развёрнут общий стенд. Фикс идёт отдельной follow-up веткой/MR, не правкой общей ветки, и верифицируется там, где баг найден. Агент заканчивается на локальных коммитах: push, саморевью перед пушем и MR - следующие шаги вне агента. Крупную пачку независимых фиксов агент распараллеливает через Agent tool; фикс, который закрывается парой вызовов, ведёт сам, и одному субагенту отдаёт фикс целиком, а не дробит на несколько.

EN: The feature is in the main branch, and the shared stand is deployed from it. The fix goes in a separate follow-up branch/MR, not as an edit to the shared branch, and is verified where the bug was found. The agent ends at local commits: push, pre-push self-review and MR are the next steps outside the agent. The agent parallelizes a large batch of independent fixes through the Agent tool; a fix that closes in a couple of calls it handles itself, and it hands one subagent a fix as a whole instead of splitting it into several.

**p2**

RU: Оракул единицы требований: судит единицу как норму и даёт вердикт для `quality-checks`. Желательность фичи по сути не судится - это решение постановщика. Дефект единицы - находка `requirement-defect`, адресованная постановщику; код под дефектный текст не правится. Метода проверки у единицы нет - вердикт единицы `unverifiable`.

EN: The oracle of a requirement unit: it judges the unit as a norm and gives the verdict for `quality-checks`. The desirability of the feature on its merits is not judged - that is the requester's decision. A unit defect is a `requirement-defect` finding addressed to the requester; code is not edited to fit defective text. If the unit has no verification method, the unit verdict is `unverifiable`.

**p3**

RU: Ядовитое сообщение блокирует партицию потребителя: после ограниченного числа попыток оно уходит на разбор (топик `*.DLT` или иное хранилище) с содержимым и причиной, смещение движется дальше; повтор на месте без предела партицию не освобождает

EN: A poison message blocks the consumer's partition: after a limited number of attempts it goes to review (a `*.DLT` topic or other storage) with its content and reason, and the offset moves on; retrying in place without a limit does not free the partition

**p4**

EN: If the group's cause cannot be derived from the batch evidence in one pass, spawn `dex-debugger:debugger` through `Agent` (`subagent_type` in the full form, a bare name does not resolve), one call per group regardless of the number of its symptoms, passing the symptom, the expected result, scope and your own `mode` (the escalation bar is inherited downward).
