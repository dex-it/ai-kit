# Скилы не открываются: хук-напоминание и где он не помогает

Исследование, ноябрь 2026. Стенд - синтетические задачи на Claude Code 2.1.326 (16-17.11), реальная
работа - сессии одного автора на рабочем проекте (C# бэкенд и фронтенд) с 01.10 по 24.11.2026 по
разбору сессий в Switchyard (личный менеджер задач автора). Имена задач и код проекта в документ
не входят.

## TL;DR

- **Проблема.** Правило в скиле есть, но скил не открывается, и правило нарушается. На рабочем
  проекте до хука основная сессия (Opus) открывала скил «как писать пользователю» в 80% сессий, где
  он был в списке, поиск по коду - в 38%, общие правила кода - в 17%, проверки перед «готово» - в 4%.
  Сабагенты: хоть один скил открыли Haiku в 35 из 59, Sonnet в 3 из 12, Opus в 0 из 6; на стенде
  сабагент Sonnet - 0 из 12.
- **Основная гипотеза.** Claude не открывает скилы по одному описанию; помогает хук-напоминание
  «пройди по списку скилов и открой подходящие» на сообщение пользователя и на старт сабагента.
  **Подтверждена** для скилов, нужда в которых видна из сообщения пользователя.
- **Реальная работа, 8 дней после хука** - доля сессий, где скил открыт, до -> после (с поправкой на
  множественность): поиск по коду 38% -> 87%, базовые факты проекта 4% -> 38%, правила C# 12% -> 40%,
  рабочие документы 5% -> 24%. Правила C# в сессиях с правкой `.cs` открыты до первой правки в 68%
  против 23%. Сабагенты-разведчики (Explore) открывали хоть один скил в 13 из 30 прогонов до хука и в
  22 из 22 после.
- **Ограничение.** Хук срабатывает только на сообщение пользователя и старт сабагента. Если правка
  понадобилась по ходу работы, а сообщение её не называло, скил правки кода не открывается ни с
  хуком, ни без (стенд, 0 из 3 в каждой серии); фраза «если задача сменится, проверь список снова»
  этого не меняет. Перед «готово» хук тоже не помог (0 из 3).

## Проблема

Разбор сессий автора 13-16.11: из 19 проблем в 7 нужное правило в скиле было, но скил не открылся.
Ещё в 2 сессиях не открылось ни одного скила.

Основная сессия (Opus) на рабочем проекте, 01.10-16.11, до хука: в скольких сессиях скил открыт из
числа сессий, где он был в списке доступных ([`real-work/problem_table.py`](real-work/problem_table.py),
выгрузка `real-work/problem.csv`).

| Открыт / был в списке | Скил | Начало описания |
| --- | --- | --- |
| 196/245 (80%) | chat-reply | «... ОБЯЗАТЕЛЬНО перед первым сообщением ...» |
| 122/273 (45%) | upcore-build | «ОБЯЗАТЕЛЬНО перед любым вызовом dotnet build / dotnet test» |
| 116/309 (38%) | code-search | «ОБЯЗАТЕЛЬНО перед первым rg / fdfind / cat ...» |
| 52/309 (17%) | code-writing | «пишу или правлю код - ...» |
| 44/273 (16%) | upcore-code | «правлю код в upcore ...» |
| 27/273 (10%) | csharp-code | «пишу или правлю C# ...» |
| 12/309 (4%) | definition-of-done | «перед словом «готово», перед сдачей задачи ...» |

Сабагенты:

- реальные сабагенты в тех же сессиях: открыл хоть один скил кита Haiku в 35 из 59, Sonnet в 3 из
  12, Opus в 0 из 6 (тот же скрипт, считаются сабагенты, у которых скилы кита были в списке);
- стенд, сабагент на синтетической задаче: Sonnet 0 из 12 прогонов, Opus 0 из 2 - не открыли даже
  скилы, которые основная сессия открывает чаще всего;
- отдельная сессия `claude -p` на тех же задачах: Sonnet открыл хоть один скил в 1 прогоне из 14
  (code-search в сценарии «объясни»), Opus - в 2 из 2 (первым действием скил ведения задачи).

Как проверяли:

- **Открыт ли скил - только по транскрипту:** в нём есть вызов инструмента `Skill` с этим скилом.
  Слова модели («открыл скил», «следую правилам») не считаются. Был ли скил в списке доступных -
  тоже по транскрипту (блок списка скилов в начале сессии).
- **Синтетические задачи.** Песочница - маленькая корзина на JS с падающим тестом
  ([`bench/cart/`](bench/cart/)). Четыре сценария с промптом, какой написал бы пользователь, без
  слова «скил»; у каждого задано, какой скил должен открыться и какой не должен
  ([`bench/scenarios.md`](bench/scenarios.md)). Каждый прогон - в своей копии песочницы, как
  сабагент или как отдельная сессия `claude -p` с тем же набором скилов, по 3 прогона на ячейку.
  Вызовы `Skill` выбирают из транскрипта скрипты [`bench/scripts/`](bench/scripts/).
- **Реальная работа.** Архивы транскриптов сессий автора в Switchyard с 01.10 по 24.11.

Первая версия этой таблицы считалась 17.11 по транскриптам другого репозитория автора за 30 дней.
Те транскрипты не сохранились, поэтому таблица заменена пересчётом по архивам Switchyard.

Вывод: скилы открываются не все и у разных моделей по-разному. Чаще открываются скилы с явным
моментом в описании («ОБЯЗАТЕЛЬНО перед первым <действие>»), реже - описания-темы («пишу или правлю
X»); это наблюдение, отдельно не проверялось.

## Гипотеза 0: скилы не доходят до модели

Если скила нет в контексте, никакое описание не поможет. Проверяли так: смотрели в транскрипте,
есть ли скил в списке доступных, спрашивали модель о скилах напрямую и давали задачу с именем скила.
**Опровергнута:**

- Когда скил назван по имени, он открывается: сабагент со списком имён в промпте открыл скилы,
  исполнитель по наряду с именами скилов открыл их до первой правки.
- В проверенной основной сессии с китом все 46 скилов в списке доступных, описания не обрезаны
  (14 192 символа). Сабагент видит тот же список и инструмент `Skill`. По архивам рабочего проекта
  у сабагентов (143 списка) описание есть у каждого скила: описания не выброшены.
- Имя скила длиннее 32 символов Claude Code в списке сокращает до 32 (`csharp-aspnet-endpo`): в
  начале октября без полного имени, позже с полным именем в скобках. Документация об этом не
  говорит: по ней при нехватке бюджета списка (1% окна контекста, настройка
  `skillListingBudgetFraction`) убираются описания редко вызываемых скилов, а имена остаются
  ([SOURCES.md](SOURCES.md), п. 4). Мешает ли сокращённое имя открыть скил, не проверяли.
- `claude -p` на Sonnet на прямой вопрос перечисляет все 14 скилов кита и дословно цитирует
  описание. Сам говорит, что вызывает скил, когда задача подходит под описание, - и не вызывает.

## Основная гипотеза: хук-напоминание

**H1.** Claude не открывает скилы по одному описанию; хук, который перед каждым сообщением
пользователя и при старте сабагента требует пройти по списку скилов, поднимает активацию.
Опровергается, если на стенде с хуком нужные скилы открываются не чаще, чем без него, а на реальной
работе доля открытия после хука в пределах случайного разброса.

Хук - плагин skill-check, события `UserPromptSubmit` и `SubagentStart` (сабагенту
`UserPromptSubmit` не приходит), текст в `additionalContext`: «Перед любым другим действием пройди
по списку доступных скилов. По описанию каждого реши, подходит ли он к этой задаче. Каждый
подходящий открой инструментом Skill сейчас, до чтения файлов и правок». Текст не зависит от
проекта.

## Что пишут другие

Похожую проблему описывают многие (список - [SOURCES.md](SOURCES.md), п. 3): скилы Claude Code
по описанию срабатывают ненадёжно, обычное обходное решение - хук `UserPromptSubmit`, который
подмешивает напоминание. Отдельно - приём из статьи Селезнёва на Medium: директивное описание
«ALWAYS invoke ... Do not X directly», по пересказам 100% срабатывания (у нас не повторилось, см.
[«Остальные проверенные гипотезы»](#остальные-проверенные-гипотезы)).

Выборка пока небольшая: на стенде по 3 прогона на ячейку, на реальной работе 8 дней после хука.
Но и на стенде, и на реальной работе изменение есть, и в одну сторону.

## Проверка на синтетических задачах

Стенд описан в разделе [«Проблема»](#проблема). Sonnet, `claude -p`, по 3 прогона.

| Сценарий | Нужный скил | Без хука | С хуком |
| --- | --- | --- | --- |
| S1 найти причину падения теста | debugging | 0/3 | 3/3 |
| S2 добавить функцию | code-writing, code-general | 0/3, 0/3 | 3/3, 3/3 |
| S3 починить тест и сказать «готово» | code-writing, definition-of-done | 0/3, 0/3 | 0/3, 0/3 |
| S4 объяснить, ничего не менять | лишних быть не должно | лишних нет | лишних нет |

- С хуком скилы открываются в начале ответа; лишних (S4) нет.
- S3: в начале ответа открыты другие скилы, code-writing - нет, ни в начале, ни перед правкой
  (0/3). Это не обязательно провал «посреди хода»: в S2 с тем же хуком code-writing открыт в начале
  3 из 3, а промпт S3 («почини тест и напиши, когда будет готово») правку не называет, и скил не
  выбран уже на старте. Без примеси формулировки установлено одно: definition-of-done перед
  «готово» не открылся (0/3).
- S5 «все тесты корзины должны проходить, разберись»: промпт правку не называет, а править
  придётся. Сабагенты Sonnet, по 3 прогона, условия сверены по транскриптам. code-writing до первой
  правки - 0/3 без хука, 0/3 с хуком, 0/3 с хуком и фразой «если задача сменится, проверь список
  снова». Скилы, если открыты, открыты первым вызовом; после того как нашлась ошибка, к списку не
  вернулся никто ([results/2026-11-25-s5-mid-turn.md](bench/results/2026-11-25-s5-mid-turn.md)).
- Сабагент с `SubagentStart`: без хука 0 скилов, с хуком - ведение задачи, debugging, chat-reply до
  первого действия (2 из 2 прогонов с одним напоминанием). code-writing перед правкой - нет.
- Цена прогона с хуком примерно вдвое выше: ~$0.15 против ~$0.075 (модель читает тексты скилов).
- Упавший прогон не спутан с «скил не открыт»: по транскриптам все 94 прогона `claude -p` и 27
  сабагентов на корзине закончились ответом, ошибок API нет (`bench/scripts/check_runs.py`).

хука в транскрипте. Сверка с датой - в выводе скрипта: до 17.11 сессий с хуком 0, с 17.11 сессий

пользователя, и хук срабатывает на каждое, поэтому в длинной сессии у скила больше поводов открыться.
По вызовам инструментов основной сессии длина почти не изменилась: медиана 43 -> 45. Доля открытия в
первом ходе сессии и в сессиях одной длины:

| Скил | В первом ходе: до -> после | 1-3 хода | 4-8 ходов | 9 и больше |
| --- | --- | --- | --- | --- |
| code-search | 35% -> 80% | 29% -> 75% | 42% -> 85% | 46% -> 96% |
| csharp-code | 3% -> 20% | 6% -> 44% | 13% -> 38% | 17% -> 38% |
| upcore | 3% -> 36% | 3% -> 0% | 3% -> 38% | 6% -> 62% |
| upcore-work-docs | 1% -> 13% | 1% -> 0% | 3% -> 15% | 10% -> 42% |

- code-search и csharp-code выросли уже в первом ходе и в сессиях любой длины: длина их рост не
  объясняет.
- upcore и upcore-work-docs в коротких сессиях после хука не открылись ни разу (0 из 16), рост
  только в длинных. Влияет ли длина или в длинных сессиях больше задач, где эти скилы нужны, по этим
  данным не разделить.

**Скилы правки кода: открыт ли до первой правки.** Правило нужно до правки, а не после, поэтому для
сессий с правкой `.cs` (95 до хука, 22 после) считается, открыт ли скил раньше первой правки
`.cs`. p здесь без поправки на множественность.

| --- | --- | --- | --- | --- |
| csharp-code | правила C# | 23% (22) -> 68% (15) | 0,0001 | 1 / 0 |
| upcore-code | правила кода проекта | 34% (32) -> 55% (12) | 0,06 | 1 / 1 |

| csharp-xml-docs | XML-комментарии `///` | 24% (23) -> 36% (8) | 0,18 | 8 / 2 |

- Если скил открывается, то почти всегда до первой правки: открытий только после правки единицы.
- Хук поднял правила C# до правки с 23% до 68%. Хук срабатывает на сообщение пользователя: если в нём
  есть правка («поправь», «добавь метод»), модель открывает правила кода сразу, как в сценарии S2
  стенда. Случай, когда правка понадобилась по ходу работы, а сообщение её не называло, здесь не
  выделить.
- В сессиях, где правки писали строки `///`, csharp-xml-docs открыт в 38% (31 из 81) до хука и в 56%
  (10 из 18) после ([`real-work/xmldocs.py`](real-work/xmldocs.py)).
- Скилы сборки и тестов открывались и до хука: при `dotnet build/test` upcore-build открыт в 97%
  сессий (113 из 117) до и в 100% (24 из 24) после, при правке теста upcore-tests - в 74% и 75%.

## Остальные проверенные гипотезы

Всё - на стенде из раздела [«Проблема»](#проблема): Sonnet, по 3 прогона на ячейку. Главная цель -
поймать момент посреди работы: скил правил кода (code-writing) перед правкой и проверки
(definition-of-done) перед словом «готово». Для этого почти везде сценарий S3 «почини падающий тест
и напиши, когда будет готово».

### Описание «что внутри + Активируется при <слова>»

- **Гипотеза.** Модель не открывает скил, потому что описание говорит о теме («пишу или правлю
  код»), а не о словах, которыми пользователь ставит задачу. Если перечислить в описании эти слова,
  скил откроется.
- **Как проверяли.** Описания четырёх скилов переписаны: что внутри и список «Активируется при
  ...». Прогоны с хуком и без, промпты на русском.
- **Результат.** Помогает, только когда слова промпта есть в описании: debugging в S1 («падает
  тест», «почему») без хука 0/3 -> 3/3. В S2 и S3 без хука 0/3, как и раньше. Скилы перед правкой
  и перед «готово» - 0/3 в любом варианте.
- **Вердикт.** Подтверждена частично: описание помогает выбрать скил в начале ответа, посреди
  работы не помогает.

### Описания на английском

- **Гипотеза.** Модель лучше понимает описания на английском.
- **Как проверяли.** Те же описания, переведённые на английский; промпты остались русскими.
- **Результат.** Не лучше русского: debugging в S1 без хука 1/3 против 3/3 у русского описания. С
  хуком разницы нет.
- **Вердикт.** Не подтверждена: на трёх прогонах разница 1/3 против 3/3 может быть случайной.
  Версия - работает совпадение слов описания и промпта, а не язык.

### Директивное описание с запретом

- **Гипотеза.** Приём из статьи Селезнёва: описание «ВСЕГДА открывай перед <действие>. Не делай
  <действие> напрямую, не открыв этот скил» даёт 100% срабатывания.
- **Как проверяли.** Так переписаны code-writing («не правь файлы с кодом через Edit, Write, sed,
  cat > файл, не открыв этот скил») и definition-of-done («не пиши «готово», не открыв этот скил»).
  S3, с хуком и без.
- **Результат.** 0/3 без хука и 0/3 с хуком у обоих скилов. Модель правит файл сразу после чтения.
- **Вердикт.** Не подтверждена на S3, где code-writing не открывает и один хук: 100% у нас не
  повторилось (условия статьи известны только по пересказам).

### Список скилов в CLAUDE.md

- **Гипотеза.** Список скилов в системном промпте модель пропускает, а CLAUDE.md читает
  внимательнее. Если положить туда строку «скил открывается в момент из его строки, в том числе
  посреди работы» и список «имя - описание», скилы будут открываться и посреди работы.
- **Как проверяли.** CLAUDE.md собран скриптом из описаний кита и положен рядом с песочницей. S3,
  с хуком и без.
- **Результат.** В начале ответа скилы открываются и без хука (3/3; без CLAUDE.md было 0 из 12).
  code-writing прямо перед правкой - 1 из 6, впервые за все серии. definition-of-done - 0 из 6.
  Цена прогона почти вдвое выше: модель читает тексты скилов.
- **Вердикт.** В начале работы подтверждена, посреди работы - почти нет (1 из 6).

### Полный список скилов в самом хуке

- **Гипотеза.** Если хук кроме напоминания отдаёт сабагенту весь список «имя - описание», сабагент
  выберет скилы точнее.
- **Как проверяли.** Хук `SubagentStart` собирал список из каталогов скилов сессии и отдавал его
  вместе с напоминанием. Варианты: список после напоминания (3 прогона), список перед
  напоминанием (2 прогона), контроль - одно напоминание без списка.
- **Результат.** Со списком - 0 из 5 прогонов открыли хоть один скил. С одним напоминанием - 2 из 2.
  Это наблюдение: прогоны не чередовали, и на 7 прогонах разница может быть случайной.
- **Вердикт.** Не подтверждена: со списком лучше не стало. Почему, не проверяли.

### Фраза в хуке «если задача сменится, проверь список снова»

- **Гипотеза.** Если хук кроме напоминания в начале попросит вернуться к списку при смене задачи
  («нашлась ошибка, пора писать код, работа закончена, пора отвечать»), модель откроет скил правки
  перед правкой.
- **Как проверяли.** S5, сабагенты Sonnet: без хука, с рабочим хуком и с хуком с этой фразой, по 3
  прогона. Хук и список скилов в каждой серии сверены по транскриптам.
- **Результат.** С фразой скилы в начале открыли 3 из 3 (рабочий хук - 1 из 3, без хука - 0 из
  3), но только первым вызовом. code-writing до правки - 0/3 во всех сериях; после найденной ошибки
  и после правки не открыто ничего
  ([results/2026-11-25-s5-mid-turn.md](bench/results/2026-11-25-s5-mid-turn.md)).
- **Вердикт.** Не подтверждена: фраза делает тщательнее проверку в начале, посреди работы не
  срабатывает. В рабочий хук не взята.

### Хуки на правку файла и на конец ответа

- **Гипотеза.** Хук на Edit/Write напомнит про скилы правки, хук на Stop - про проверки перед
  «готово».
- **Результат.** Отвергнута без прогона: все сабагенты в S3 правили код через Bash (`cat > файл`),
  хук на Edit/Write такую правку не увидит. Кроме того, это много мест для поддержки.
- **Вердикт.** Не проверялась прогоном.

### Поле `paths` во frontmatter скила

- **Гипотеза.** По документации скил с `paths` загружается сам, когда модель работает с подходящими
  файлами. Это решило бы момент «перед правкой».
- **Как проверяли.** Тестовый скил с `paths` и файлом-приманкой (`bench/paths-plugin/`), сабагент
  читает файл.
- **Результат.** Текст скила сам не подмешивается. До чтения файла скила нет в списке, после -
  появляется строка с его описанием, а открывать его модель по-прежнему решает сама.
- **Вердикт.** Опровергнута: `paths` прячет скил из списка, а не загружает его.

## Ограничения и открытые вопросы

- **Посреди хода хук не помогает.** Он срабатывает на сообщение пользователя и старт сабагента;
  если в сообщении названо действие, шанс открыть нужный скил сильно выше. Перед правкой кода и
  перед «готово» модель сама к списку не возвращается: в S5 правка понадобилась по ходу работы, и
  code-writing не открыт ни с хуком, ни без (0 из 3 в каждой серии). Ни описания, ни CLAUDE.md, ни
  директивные формулировки, ни фраза хука «при смене задачи проверь снова» этот момент не ловят
  (лучшее - 1-2 случая из 6). Research gap.
- **Большие наборы скилов.** Версия, что модель хуже выбирает из длинного списка, не проверена.
  Research gap.
- **Назвать скилы по имени или подать заранее.** Вместо напоминания можно назвать скилы по имени в
  задании сабагенту (наряд) или подать их агенту заранее (pre-load), как в аудите загрузки скилов в
  каталоге ([SOURCES.md](SOURCES.md), п. 2). Это не проверяли. Видно только одно: исполнитель с
  именами скилов в наряде открыл их до первой правки (стенд, 1 прогон, хук тоже был). Замер
  pre-load вынесен в ai-kit#131.

## Угрозы валидности

- **Выборка небольшая.** На стенде по 3 прогона на ячейку, на реальной работе 8 дней после хука;
  один автор и один проект.
- **Периоды неравные.** До хука 47 дней, после 8. За это время менялись набор скилов и версия
  Claude Code. Набор учтён: доля скила считается по сессиям, где он был в списке доступных. Версия
  не учтена.
- **Автор знал про хук** и мог иначе ставить задачи после его включения.
- **Разбивка выбрана после результата.** Скилы для таблиц и деление на «нужны с начала» и «нужны
  посреди хода» сделаны, когда числа уже были видны. Поправка на множественность учитывает все
  строки таблицы, но не само деление.
- **Метрика - открытие скила, а не соблюдение правила.** Проблема сформулирована как «правило
  нарушается», а измерено, открыт ли скил. Соблюдение правил после хука не измерялось.
- **Сессии после хука длиннее** по ходам (медиана 5 -> 8). Для части скилов рост виден только в
  длинных сессиях; см. разбивку по длине в [«Проверке на реальной работе»](#проверка-на-реальной-работе).
- **Цена хука на реальной работе не измерена.** На стенде прогон с хуком примерно вдвое дороже.
- **Предрегистрации нет.** План повторной проверки будет записан до её начала.

### Команды

Пересчитать реальную работу можно только при данных автора: база Switchyard с разбором сессий
(`~/.switchyard/switchyard.db`), архивы транскриптов (`~/.switchyard/traces`) и утилита `zstd`.
Без них проверяется только расчёт по готовым csv. Копию базы снимать через backup API SQLite: база
открыта приложением.

```bash
python3 -c "import sqlite3; s=sqlite3.connect('$HOME/.switchyard/switchyard.db'); d=sqlite3.connect('sy.db'); s.backup(d)"
cd real-work
python3 export.py sy.db         # sessions.csv, subagent-runs.csv
python3 activation.py sy.db     # доли до и после хука, p, Холм, до первой правки, по длине; activation.json
python3 problem_table.py sy.db  # таблица «Проблема» до хука; problem.csv
python3 xmldocs.py sy.db        # сессии с записью `///`: открыт ли csharp-xml-docs
python3 ../bench/scripts/check_runs.py   # прогоны стенда: ошибки API, закончились ли ответом
```

Конец окна (`END_DAY`), признак хука и разбор списка скилов - в `real-work/traces.py`; список
репозиториев и поводы для скилов - в начале `real-work/activation.py`.
