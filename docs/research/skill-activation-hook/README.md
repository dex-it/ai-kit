# Скилы не открываются: хук-напоминание и где он не помогает

Исследование, ноябрь 2026. Стенд - синтетические задачи на Claude Code 2.1.326 (16-17.11), реальная
работа - сессии одного автора на рабочем проекте (C# бэкенд и фронтенд) с 01.10 по 19.11.2026 по
разбору сессий в Switchyard (личный менеджер задач автора). Имена задач и код проекта в документ
не входят.

## TL;DR

- **Проблема.** Правило в скиле есть, но скил не открывается, и правило нарушается. Сабагенты
  на Sonnet и Haiku не открывают скилы почти никогда. Opus в основной сессии открывает не все:
  одни скилы в 31-73% сессий, правила кода и проверки перед «готово» - почти никогда (code-writing
  5 из 45, definition-of-done 0 из 45, правила C# 0 из 25).
- **Основная гипотеза.** Claude не открывает скилы по одному описанию; помогает хук-напоминание
  «пройди по списку скилов и открой подходящие» на сообщение пользователя и на старт сабагента.
  **Подтверждена** для скилов, нужных с начала работы.
- **Лучшие активации на реальной работе (3 дня после хука)** - доля сессий, где скил открыт, до ->
  после: поиск по коду 38% -> 88%, базовые факты проекта 4% -> 38%, рабочие документы 5% -> 25%.
  Сабагенты-разведчики (Explore) открывали хоть один скил в 43% прогонов до хука (13 из 30) и во
  всех после (13 из 13).
- **Ограничение.** Хук срабатывает только на сообщение пользователя и старт сабагента. Посреди хода
  модели - перед правкой кода, перед «готово» - он не помогает, и ни один проверенный способ
  этот момент не ловит. Это открытый вопрос (research gap).

## Проблема

Разбор сессий автора 13-16.11: из 19 проблем в 7 нужное правило в скиле было, но скил не открылся.
Ещё в 2 сессиях не открылось ни одного скила.

Основная сессия (Opus), транскрипты за 30 дней: сколько раз скил открыт из числа сессий, где он был
в списке доступных.

| Открыт / был в списке | Скил | Начало описания |
| --- | --- | --- |
| 33/45 | chat-reply | «... ОБЯЗАТЕЛЬНО перед первым сообщением ...» |
| 12/25 | upcore-build | «ОБЯЗАТЕЛЬНО перед любым вызовом dotnet build / dotnet test» |
| 18/45 | code-search | «ОБЯЗАТЕЛЬНО перед первым rg / fdfind / cat ...» |
| 5/45 | code-writing | «пишу или правлю код - ...» |
| 0/45 | definition-of-done | «перед словом «готово», перед сдачей задачи ...» |
| 0/25 | csharp-*, upcore-code и др. | «пишу или правлю C# ...», «правлю код в upcore ...» |

Сабагенты открывают ещё реже:

- реальные сабагенты за 30 дней: Sonnet - 1 из 10 (и у того список скилов был прямо в промпте),
  Haiku - 4 из 14;
- стенд, сабагент на синтетической задаче: Sonnet 0 из 12 прогонов, Opus 0 из 2 - не открыли даже
  скилы, которые основная сессия открывает чаще всего;
- отдельная сессия `claude -p` на тех же задачах: Sonnet открыл хоть один скил в 1 прогоне из 14
  (code-search в сценарии «объясни»), Opus - в 2 из 2 (первым действием скил ведения задачи).

Как проверяли:

- **Открыт ли скил - только по транскрипту:** в нём есть вызов инструмента `Skill` с этим скилом.
  Слова модели («открыл скил», «следую правилам») не считаются. Был ли скил в списке доступных -
  тоже по транскрипту (блок списка скилов в начале сессии).
- **Синтетические задачи.** Песочница - маленькая корзина на JS с падающим тестом
  ([`bench/cart/`](bench/cart/)). Четыре сценария с промптом, какой написал бы пользователь, без
  слова «скил»; у каждого задано, какой скил должен открыться и какой не должен
  ([`bench/scenarios.md`](bench/scenarios.md)). Каждый прогон - в своей копии песочницы, как
  сабагент или как отдельная сессия `claude -p` с тем же набором скилов, по 3 прогона на ячейку.
  Вызовы `Skill` выбирают из транскрипта скрипты [`bench/scripts/`](bench/scripts/).
- **Реальная работа.** Транскрипты сессий автора: за 30 дней до исследования и по разбору сессий
  в Switchyard с 01.10 по 19.11.

Вывод: Opus открывает скилы чаще Sonnet и Haiku, но и он открывает не все. Чаще открываются скилы
с явным моментом в описании («ОБЯЗАТЕЛЬНО перед первым <действие>»), реже - описания-темы («пишу
или правлю X»); это наблюдение, отдельно не проверялось.

## Гипотеза 0: скилы не доходят до модели

Если скила нет в контексте, никакое описание не поможет. Проверяли так: смотрели в транскрипте,
есть ли скил в списке доступных, спрашивали модель о скилах напрямую и давали задачу с именем скила.
**Опровергнута:**

- Когда скил назван по имени, он открывается: сабагент со списком имён в промпте открыл скилы,
  исполнитель по наряду с именами скилов открыл их до первой правки.
- В сессии с китом все 46 скилов в списке доступных, описания не обрезаны (14 192 символа).
  Сабагент видит тот же список и инструмент `Skill`.
- `claude -p` на Sonnet на прямой вопрос перечисляет все 14 скилов кита и дословно цитирует
  описание. Сам говорит, что вызывает скил, когда задача подходит под описание, - и не вызывает.

## Основная гипотеза: хук-напоминание

**H1.** Claude не открывает скилы по одному описанию; хук, который перед каждым сообщением
пользователя и при старте сабагента требует пройти по списку скилов, поднимает активацию.
Опровергается, если на стенде с хуком нужные скилы открываются не чаще, чем без него, а на реальной
работе доля открытия после хука в пределах случайного разброса.

Хук - плагин skill-check, события `UserPromptSubmit` и `SubagentStart` (сабагенту
`UserPromptSubmit` не приходит), текст в `additionalContext`: «Перед любым другим действием пройди
по списку доступных скилов. По описанию каждого реши, подходит ли он к этой задаче. Каждый
подходящий открой инструментом Skill сейчас, до чтения файлов и правок». Текст не зависит от
проекта.

## Что пишут другие

Похожую проблему описывают многие (список - [SOURCES.md](SOURCES.md), п. 3): скилы Claude Code
по описанию срабатывают ненадёжно, обычное обходное решение - хук `UserPromptSubmit`, который
подмешивает напоминание. Отдельно - приём из статьи Селезнёва на Medium: директивное описание
«ALWAYS invoke ... Do not X directly», по пересказам 100% срабатывания (у нас не повторилось, см.
[«Остальные проверенные гипотезы»](#остальные-проверенные-гипотезы)).

Выборка пока небольшая: на стенде по 3 прогона на ячейку, на реальной работе 3 дня после хука.
Но и на стенде, и на реальной работе изменение есть, и в одну сторону.

## Проверка на синтетических задачах

Стенд описан в разделе [«Проблема»](#проблема). Sonnet, `claude -p`, по 3 прогона.

| Сценарий | Нужный скил | Без хука | С хуком |
| --- | --- | --- | --- |
| S1 найти причину падения теста | debugging | 0/3 | 3/3 |
| S2 добавить функцию | code-writing, code-general | 0/3, 0/3 | 3/3, 3/3 |
| S3 починить тест и сказать «готово» | code-writing, definition-of-done | 0/3, 0/3 | 0/3, 0/3 |
| S4 объяснить, ничего не менять | лишних быть не должно | лишних нет | лишних нет |

- С хуком скилы открываются в начале ответа; лишних (S4) нет.
- S3: все скилы открыты в начале, потом правка и «Готово». Перед правкой и перед «готово» скилы не
  открывались. Строка «при смене задачи проверь снова» не сработала.
- Сабагент с `SubagentStart`: без хука 0 скилов, с хуком - ведение задачи, debugging, chat-reply до
  первого действия (2 из 2 прогонов с одним напоминанием). code-writing перед правкой - нет.
- Цена прогона с хуком примерно вдвое выше: ~$0.15 против ~$0.075 (модель читает тексты скилов).

## Проверка на реальной работе

Хук включён 17.11. Сравнение: 01.10-16.11 против 17.11-19.11, бэкенд проекта: 231 сессия до, 24
после (фронтенд - 80 и 6, для выводов мало). Хук есть во всех сессиях после 17.11 и ни в одной
до (проверено по транскриптам). Окно 31.10-08.11 пустое: работа шла с другого компьютера.

Две доли на скил:
- **«Открыт, доля всех сессий»** - зависит от того, сколько было работы нужного вида;
- **«Открыт, когда был нужен»** - только среди сессий, где было действие, под которое скил написан
  (правка `.cs`, `dotnet build`, запрос через `psql`, запись `///` в правке). Это и есть доля
  активации; действие задано не для всех скилов.

p - односторонняя биномиальная проверка: как часто сдвиг не меньше наблюдаемого выходит случайно,
если доля после хука равна доле до. Порог 5%.

| Скил | Что это | Открыт, доля всех сессий: до -> после | p | Когда скил нужен | Открыт, когда был нужен: до -> после |
| --- | --- | --- | --- | --- | --- |
| code-search | поиск и чтение кода | 38% -> 88% | <0,001 | читали код | 38% -> 91% |
| upcore | базовые факты проекта | 4% -> 38% | <0,001 | - | - |
| upcore-work-docs | рабочие документы задачи | 5% -> 25% | <0,001 | - | - |
| csharp-aspnet-endpoints | эндпоинты ASP.NET | 1% -> 12% | 0,001 | - | - |
| upcore-naming | имена роутов, DTO, методов | 5% -> 21% | 0,007 | - | - |
| chat-reply | как писать пользователю | 83% -> 96% | 0,06 | - | - |
| task-implementation | ведение задачи: карточка, план | 26% -> 42% | 0,08 | - | - |
| definition-of-done | проверки перед «готово» | 4% -> 12% | 0,08 | - | - |
| postgres-reader | запросы к базе | 19% -> 38% | 0,03 | запрос через psql | 91% -> 100% |

- **Скилы начала работы выросли надёжно.** С поправкой на множественность (около 30 скилов,
  порог 0,05/30) держатся четыре: code-search, upcore, upcore-work-docs, csharp-aspnet-endpoints.
- **Рост не от размера сессий:** медиана вызовов инструментов 38 -> 30,5, ходов 5 -> 7.

Скилы, которые нужны посреди хода модели - перед сборкой, перед правкой кода или теста. Здесь
считается только доля «когда был нужен»: общая доля у них зависит от того, сколько в эти дни
собирали и правили. Данных после хука мало, но изменения не видно. На стенде то же: в сценарии
S3 скилы перед правкой и перед «готово» не открылись ни без хука, ни с ним (0 из 3).

| Скил | Что это | Когда скил нужен | Открыт, когда был нужен: до -> после |
| --- | --- | --- | --- |
| upcore-build | сборка и прогон тестов | запускали `dotnet build/test` | 97% (113 из 117) -> 100% (6 из 6) |
| upcore-tests | тесты проекта | правили тест | 74% (51 из 69) -> 75% (3 из 4) |
| upcore-code | правила кода проекта | правили `.cs` | 35% (33 из 95) -> 50% (3 из 6) |
| csharp-xml-docs | XML-комментарии `///` | писали или правили `///` | 38% (31 из 81) -> 25% (1 из 4) |
| code-writing | общие правила при написании кода | правили любой файл | 33% (43 из 130) -> 14% (2 из 14) |

Ни один сдвиг здесь не проходит порог 5%: при прежней доле такой результат случайно выходит в
11-81% случаев.

Сабагенты (вид определён по описанию прогона):

| Вид прогона | До: прогонов | со скилами | После: прогонов | со скилами |
| --- | --- | --- | --- | --- |
| Разведка (Explore) | 30 | 13 (43%) | 13 | 13 (100%) |
| Исполнитель по наряду | 22 | 17 (77%) | 8 | 8 (100%) |
| Ревьюер | 12 | 3 (25%) | 4 | 1 (25%) |
| Прочие | 18 | 5 (28%) | 4 | 4 (100%) |

Вид прогона - по описанию (функция `run_kind` в `real-work/export.py`): тип Explore - разведка,
слова «Наряд», «Реализация», «Тесты» и т. п. - исполнитель, «Ревью» - ревьюер. У разведки 13 из 13
при базе 43% случайно выходит с вероятностью около 0,002%. Исполнители
открывали скилы и до хука: наряд называет их по имени (та же картина, что в «Гипотезе 0»).

## Остальные проверенные гипотезы

Всё - на стенде из раздела [«Проблема»](#проблема): Sonnet, по 3 прогона на ячейку. Главная цель -
поймать момент посреди работы: скил правил кода (code-writing) перед правкой и проверки
(definition-of-done) перед словом «готово». Для этого почти везде сценарий S3 «почини падающий тест
и напиши, когда будет готово».

### Описание «что внутри + Активируется при <слова>»

- **Гипотеза.** Модель не открывает скил, потому что описание говорит о теме («пишу или правлю
  код»), а не о словах, которыми пользователь ставит задачу. Если перечислить в описании эти слова,
  скил откроется.
- **Как проверяли.** Описания четырёх скилов переписаны: что внутри и список «Активируется при
  ...». Прогоны с хуком и без, промпты на русском.
- **Результат.** Помогает, только когда слова промпта есть в описании: debugging в S1 («падает
  тест», «почему») без хука 0/3 -> 3/3. В S2 и S3 без хука 0/3, как и раньше. Скилы перед правкой
  и перед «готово» - 0/3 в любом варианте.
- **Вердикт.** Подтверждена частично: описание помогает выбрать скил в начале ответа, посреди
  работы не помогает.

### Описания на английском

- **Гипотеза.** Модель лучше понимает описания на английском.
- **Как проверяли.** Те же описания, переведённые на английский; промпты остались русскими.
- **Результат.** Хуже русского: debugging в S1 без хука 1/3 против 3/3 у русского описания. С хуком
  разницы нет.
- **Вердикт.** Опровергнута: работает совпадение слов описания и промпта, а не язык сам по себе.

### Директивное описание с запретом

- **Гипотеза.** Приём из статьи Селезнёва: описание «ВСЕГДА открывай перед <действие>. Не делай
  <действие> напрямую, не открыв этот скил» даёт 100% срабатывания.
- **Как проверяли.** Так переписаны code-writing («не правь файлы с кодом через Edit, Write, sed,
  cat > файл, не открыв этот скил») и definition-of-done («не пиши «готово», не открыв этот скил»).
  S3, с хуком и без.
- **Результат.** 0/3 без хука и 0/3 с хуком у обоих скилов. Модель правит файл сразу после чтения.
- **Вердикт.** Опровергнута: 100% у нас не повторилось (условия статьи известны только по
  пересказам).

### Список скилов в CLAUDE.md

- **Гипотеза.** Список скилов в системном промпте модель пропускает, а CLAUDE.md читает
  внимательнее. Если положить туда строку «скил открывается в момент из его строки, в том числе
  посреди работы» и список «имя - описание», скилы будут открываться и посреди работы.
- **Как проверяли.** CLAUDE.md собран скриптом из описаний кита и положен рядом с песочницей. S3,
  с хуком и без.
- **Результат.** В начале ответа скилы открываются и без хука (3/3; без CLAUDE.md было 0 из 12).
  code-writing прямо перед правкой - 1 из 6, впервые за все серии. definition-of-done - 0 из 6.
  Цена прогона почти вдвое выше: модель читает тексты скилов.
- **Вердикт.** В начале работы подтверждена, посреди работы - почти нет (1 из 6).

### Полный список скилов в самом хуке

- **Гипотеза.** Если хук кроме напоминания отдаёт сабагенту весь список «имя - описание», сабагент
  выберет скилы точнее.
- **Как проверяли.** Хук `SubagentStart` собирал список из каталогов скилов сессии и отдавал его
  вместе с напоминанием. Варианты: список после напоминания (3 прогона), список перед
  напоминанием (2 прогона), контроль - одно напоминание без списка.
- **Результат.** Со списком - 0 из 5 прогонов открыли хоть один скил. С одним напоминанием - 2 из 2.
- **Вердикт.** Опровергнута, со списком хуже. Почему, не проверяли. Версия: длинный перечень
  читается как справка, и требование в нём теряется.

### Хуки на правку файла и на конец ответа

- **Гипотеза.** Хук на Edit/Write напомнит про скилы правки, хук на Stop - про проверки перед
  «готово».
- **Результат.** Отвергнута без прогона: все сабагенты в S3 правили код через Bash (`cat > файл`),
  хук на Edit/Write такую правку не увидит. Кроме того, это много мест для поддержки.
- **Вердикт.** Не проверялась прогоном.

### Поле `paths` во frontmatter скила

- **Гипотеза.** По документации скил с `paths` загружается сам, когда модель работает с подходящими
  файлами. Это решило бы момент «перед правкой».
- **Как проверяли.** Тестовый скил с `paths` и файлом-приманкой (`bench/paths-plugin/`), сабагент
  читает файл.
- **Результат.** Текст скила сам не подмешивается. До чтения файла скила нет в списке, после -
  появляется строка с его описанием, а открывать его модель по-прежнему решает сама.
- **Вердикт.** Опровергнута: `paths` прячет скил из списка, а не загружает его.

## Ограничения и открытые вопросы

- **Посреди хода хук не помогает.** Он срабатывает на сообщение пользователя и старт сабагента;
  если в сообщении названо действие, шанс открыть нужный скил сильно выше. Перед правкой кода и
  перед «готово» модель сама к списку не возвращается. Ни описания, ни CLAUDE.md, ни директивные
  формулировки этот момент не ловят (лучшее - 1-2 случая из 6). Research gap.
- **Большие наборы скилов.** Версия, что модель хуже выбирает из длинного списка, не проверена.
  Research gap.
- Что работает вместо этого: назвать скилы по имени в задании сабагенту (наряд), подать их заранее,
  как в аудите загрузки скилов в каталоге ([SOURCES.md](SOURCES.md), п. 2), или проверять готовый
  результат ревьюером по тем же скилам.

## Угрозы валидности

Выборка пока небольшая: на стенде по 3 прогона на ячейку, на реальной работе 3 дня после хука,
один автор и один проект.

### Команды

Реальная работа пересчитывается по базе Switchyard с разбором сессий и архивами транскриптов
(`~/.switchyard`). Копию базы снимать через backup API SQLite: база открыта приложением.

```bash
python3 -c "import sqlite3; s=sqlite3.connect('$HOME/.switchyard/switchyard.db'); d=sqlite3.connect('sy.db'); s.backup(d)"
cd real-work
python3 export.py sy.db       # sessions.csv, subagent-runs.csv
python3 activation.py sy.db   # доли по скилам до и после хука, p; пишет activation.json
python3 xmldocs.py sy.db      # сессии с записью `///`: открыт ли csharp-xml-docs
```

Граница хука, окно без данных у chat-reply и список репозиториев - константы в начале
`real-work/activation.py`.
