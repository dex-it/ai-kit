Две проблемы, обратные друг другу: агент делает больше, чем просили, и агент объявляет успех, не доказав его. Решаются они одним инструментом - формулировкой границы и критерия «готово» в проверяемой форме.

## Граница объёма

Модели последнего поколения склонны расширять задачу: дописывать защитные проверки, чинить соседнее, добавлять незаказанные шаги. Особенно когда у исполнителя есть «давящая» роль (старший инженер, ревьюер, который должен найти проблемы). Лечится это одной строкой.

**Что измерено.** В пилотных замерах каталога (малые серии, 15 кейсов): когда в теле агента есть роль, строка о границе поднимала долю пройденных проверок границы с 0,72 до 0,84 у небольшой модели и с 0,50 до 0,93 у средней. Когда роли нет, обе формы на потолке: встроенный системный промт Claude Code уже держит объём. Значит, строка о границе нужна узким агентам с ролью (фиксер, ревьюер), а не «любому промту» ([предварительная регистрация стенда, итоги пилота](https://github.com/dex-it/ai-kit/blob/develop/tests/eval55/PREREG.md#что-показал-пилот)). Итогов полной серии по границе в README стенда нет; пилотные числа - ориентир.

**Как писать границу.**

- Что входит: «правка в модуле экспорта».
- Что не входит: «миграции схемы и соседние экспорты не трогаем».
- Что делать с замеченным рядом: «в список открытых наблюдений, не в эту правку». Так устроены команды каталога: `/dex-implement:implement` держит скоуп равным ТЗ или плану, замеченное рядом уходит в наблюдения.
- Какой исход допустим, если делать нечего: «менять нечего» - законный результат, называется с причиной. Без этого агент придумывает правку, чтобы не вернуться с пустыми руками.

Агенты каталога несут раздел `Boundaries`: что не делают, когда возвращают `blocked`, что требует подтверждения. Для узких агентов (фиксер, ревьюер) там явная строка о границе и допустимом «менять нечего».

## Остановки: что агент не делает сам

Граница действий, а не только объёма. Перечень, общий для всего каталога:

| Действие | Правило |
|---|---|
| push | только по явной команде или флагу (`пушь`, `--pr`) |
| merge, approve, деплой, миграции данных, необратимое удаление | не выполняются, прогон останавливается и называет такой шаг |
| запись в чужой MR или тикет | только по санкции (`оформляй`, `пушь`, `--post`) |
| мутация общего стенда | отдельное подтверждение на каждое действие |
| выбор между технически равными альтернативами | неблокирующий вопрос: предъявить и идти дальше |
| бюджетная рамка, приоритет между конфликтующими требованиями | блокирующий вопрос оператору |

Различие важно: невыводимое бизнес-решение блокирует работу (спрашиваем), равноценный технический выбор - нет (принимаем и записываем в журнал решений с основанием).

## Проверяемое «готово»

«Готово» без проверки - мнение модели. Критерий пишется так, чтобы любой мог проверить его, не читая код правки:

| Задача | Слабый критерий | Проверяемый |
|---|---|---|
| исправить баг | «баг исправлен» | воспроизводящий тест был красным и стал зелёным; сборка и тесты проходят |
| фича | «фича работает» | каждое требование тикета закрыто тестом; сборка и тесты проходят |
| ревью | «посмотрел» | каждая находка проверена вторым проходом по коду, неподтверждённые вынесены в «перепроверить» |
| приёмка на стенде | «деплой зелёный» | наблюдаемое поведение по каждому требованию ТЗ |
| документация | «описал» | факты сверены с кодом, расхождения названы |

### Внешний факт

Рабочий критерий: **какой факт извне появляется по итогу шага?** Если ответа нет, шаг - самоперечитывание, и ценность у него нулевая: новые модели проверяют себя сами, а повторная просьба «убедись ещё раз» складывается с их собственной проверкой и даёт лишний проход. Если ответ есть (прогон тестов, сборка, линтер, сверка с источником, проверка находки независимым агентом), это законная петля верификации.

Так устроен `dex-auto`: готовность подтверждает прогон сборки и тестов скриптом, а не слово модели; находки ревью проверяет второй агент (скептик) по коду; сдача исхода пишется скриптом. В приёмке на стенде зелёный деплой, чистый merge, поды `Running` и health 200 доказательством не считаются: статус даёт наблюдаемое поведение.

### Честные статусы

Каждая единица работы возвращает исход машинно различимым первым полем: `complete`, `blocked`, `partial`. Всё, что нельзя довести, называется, а не замалчивается:

- `blocked` - не хватает входа; причина названа строкой, что дать, чтобы продолжить;
- `partial` - доведено не всё: у каждой открытой находки есть решение «отложено» или «блокирует»;
- `unverifiable` - проверка невозможна (нет оракула, источник недоступен), причина записана;
- `n/a` с причиной - проверка к случаю неприменима.

Молчание считается дефектом. Если агент вернул «всё хорошо» без перечня того, что проверялось и чего не хватило, спросите перечень.

## Продолжение и возврат

Недоведённая работа не теряется: `/dex-auto:auto TASK продолжить` начинает с проверки текущего дерева (зелёное с коммитами не переделывается, красное идёт на доработку), состояние лежит в журнале вне репозитория. Это удобная модель для любой работы: фиксируйте, что сделано и проверено, и продолжайте с проверки состояния, а не с доверия к прошлому разговору.
