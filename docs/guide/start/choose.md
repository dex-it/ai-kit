В каталоге много плагинов, и ставить всё не нужно: каждый включённый плагин присутствует в контексте каждой сессии своими описаниями ([Контекст: что и когда загружается](/architecture/context-loading/)). Выбор делается по роли и задаче.

## Выбор по роли

В колонке «Состав» первое число - профиль роли (то, ради чего бандл собран), второе - всего плагинов с подтянутыми зависимостями. «Листинг» - суммарное число знаков описаний skills, агентов и команд бандла, то есть постоянный платёж в контексте (замер `npm run measure:listing -- --bundles`).

| Я - ... | Бандл | Состав | Листинг, знаков | Что даёт |
|---|---|---|---:|---|
| разработчик на .NET | `dotnet-developer` | 20 / 77 | 33 315 | дизайн, реализация, тесты, EF Core, ревью своего и чужого, баги, инциденты |
| разработчик на .NET с инфраструктурой | `dotnet-fullstack` | 32 / 96 | 40 735 | то же плюс Kubernetes, Kafka, RabbitMQ, Redis, Mongo, Postgres, Seq, Grafana |
| разработчик на TypeScript | `ts-fullstack` | 13 / 57 | 24 583 | реализация, тесты, ревью, баги; Node.js, Bun, React |

| хочу отдавать задачи целиком | `auto` | 8 / 23 | 14 463 | `/dex-auto:onboard`, `/goal`, `/auto`: треки feature, bugfix, ревью |

Бандл `market-editor` предназначен для автора каталога, обычному пользователю не нужен.

Бандлы могут пересекаться: скрипт установки уже поставленные плагины пропускает. Значит, второй бандл докупает только разницу, но и платёж в контекст суммируется.

## Выбор по задаче

Если вы начинаете с конкретной задачи, а не с роли, выбор сделан в [Сценариях](/scenarios/): для каждого указан бандл и команда. Коротко:

| Задача | Минимальный набор |
|---|---|
| проверить свою ветку перед push | `code-review` (или бандл разработки вашего стека) |
| отревьюить чужой MR | `code-review` |
| разобраться в незнакомом проекте | `architect` |
| собрать требования | `system-analyst` |
| спроектировать решение | `architect` |
| реализовать фичу | `dotnet-developer` или `ts-fullstack` (нужен кодер вашего стека) |
| принять фичу на стенде | `qa-engineer`, `code-review` или `bug-lifecycle` |
| найти и объяснить баг | `bug-lifecycle` |
| отдать задачу целиком | `auto` |

Кодеры и тестописатели есть для .NET и TypeScript. На других стеках работают общие специалисты (ревью, поиск багов, дизайн), а `/dex-implement:implement` и `/dex-test:test` остановятся и назовут недостающий плагин.

## Один плагин вместо бандла

Берите отдельный плагин, если нужна одна вещь:

- **одна памятка по стеку** (`dex-skill-redis`) - один плагин без лишнего;
- **одна CLI-команда** (`dex-kubectl-cli`) - обёртка над `kubectl`;
- **мод** (`dex-github-pr-tracker`) - в бандлы ролей они не входят.

Специалиста лучше ставить бандлом: поодиночке он запустится, но без своих skills будет работать вслепую, а `claude plugin install` каскада не делает. Увидеть недостающие skills у уже установленных специалистов можно через `./install-bundle/sync-plugins.sh` ([Обновление и удаление](/start/update-remove/)).

## Как не поставить лишнее

1. Начните с одного бандла по главной роли. Добавляйте второй, когда упёрлись в конкретную команду.
2. Посмотрите состав без установки: `./install-bundle/install-bundle.sh <имя> --dry-run`.
3. Оцените цену плагина: `claude plugin details <имя>` показывает состав и ожидаемую стоимость в токенах.
4. Ненужное отключайте, не удаляя: `claude plugin disable <имя>`.
5. Если ответы стали хуже на длинных сессиях, проверьте строку Skills в `/context` и `/doctor` ([Контекст](/architecture/context-loading/)).

## Если вашей роли нет

Роль, которой нет в таблице, собирается из плагинов: найдите команды в [каталоге команд](/catalog/commands/), поставьте их плагины и нужные skills. Для специалиста найдите бандл, в который он входит (это видно на его странице в каталоге): так вместе с ним приедут его skills. Если не хватает целого стека, [добавьте плагин](/authoring/): новый стек - это новые skills и строка реестра, а не правка агентов.
