Одна задача проходит несколько этапов, и у каждого есть своя команда-вход. Страница показывает цепочку целиком, чтобы было видно, что чем заканчивается и что передаётся дальше. Каждый этап можно пройти отдельно или целиком отдать автономному треку ([Отдать задачу целиком](/scenarios/auto/)).

```text
идея -> требования -> дизайн -> реализация -> тесты -> саморевью -> MR
                                                                     |
          приёмка на стенде <- правки по ревью <- ревью чужого <-----+
                  |
        баги и инциденты -> причина -> исправление -> (обратно в реализацию)
```

## Этапы и команды

| Этап | Команда | Принимает | Отдаёт | Бандл |
|---|---|---|---|---|
| Разведка (если проект незнаком) | `/dex-code-discovery:discover`, `/dex-codebase-analyzer:codebase-summary` | путь к проекту | карта проблем, сводка стека | `architect`, `dotnet-developer` |
| Требования | `/dex-business-analyst:feature` | идея, тема, чужой документ, правка принятого | цели, сценарии, правила, истории с критериями приёмки, журнал решений | `system-analyst`, `product-manager` |
| Проверка требований | `/dex-requirements-reviewer:feature-check` | собранный набор требований | вердикты по единицам и набору, готовность к разработке | `system-analyst`, `product-manager` |
| Дизайн | `/dex-architect:design` | задача или принятые требования | дизайн-документ с альтернативами, план реализации, ADR и диаграммы по надобности | `architect`, `dotnet-developer`, `system-analyst` |
| Реализация | `/dex-implement:implement` | ТЗ, тикет или пути плана и дизайна | серия локальных коммитов, отчёт | `dotnet-developer`, `ts-fullstack`, `dotnet-fullstack` |
| Тесты | `/dex-test:test` | путь или diff | тесты, покрытие по осям | те же и `qa-engineer`, `code-review` |
| Саморевью | `/dex-self-reviewer:self-review` | база для сравнения | чеклист правок до push | `code-review` и бандлы разработки |
| Ревью чужого MR | `/dex-mr-reviewer:mr-review` | ссылка на MR | находки, черновики тредов | `code-review` и бандлы разработки |
| Обработка ревью | `/dex-review-planner:review-plan` | ссылка на MR с замечаниями | план P0-P3, правки, ответы в треды | `code-review` и бандлы разработки |
| Приёмка на стенде | `/dex-stand-reviewer:review-stand` | ТЗ, ветка стенда | карта требований, проблемы, ремедиация | `qa-engineer`, `code-review`, `bug-lifecycle` |
| Поиск багов в фиче | `/dex-bug-finder:find-bugs` | фича или ветка | найденные дефекты с воспроизведением | `bug-lifecycle`, `qa-engineer` |
| Причина бага | `/dex-debugger:root-cause` | симптом | причина, прошедшая опровержение | `bug-lifecycle` и др. |
| Инцидент на стенде | `/dex-incident-investigator:investigate` | симптом, доступ к стенду | цепочка причин, фальсификация | `bug-lifecycle` |
| Автономно: цель и трек | `/dex-auto:goal`, `/dex-auto:auto` | тикет, спецификация, симптом | коммиты (и PR с `--pr`), документация | `auto` |

Что стоит за стрелками:

- **Требования -> дизайн.** Дизайн берёт принятые требования (`FR`, `NFR`) или бизнес-задачу в свободной форме; вход только с целями без системного уровня принимается как задача, а выведенные `FR`/`NFR` помечаются допущениями.
- **Дизайн -> реализация.** Выход `/dex-architect:design` (пути одобренного плана, дизайн-документа и журнала решений) прямо подходит на вход `/dex-implement:implement`: решение заново не выводится, шаги плана берутся как есть. Без плана команда сама строит edit-план.
- **Реализация -> тесты.** `/dex-implement:implement` ведёт тесты своим тестописателем; `/dex-test:test` отдельно закрывает матрицу покрытия по осям (happy-path, негатив, краевые, ветки).
- **Реализация -> ревью.** Финиш реализации - локальные коммиты, push и MR отдельно; перед ними `/dex-self-reviewer:self-review`, который разрешает `пушь` только при зелёном прогоне и вердикте `APPROVE`.
- **Ревью -> правки.** Автор получает замечания и идёт через `/dex-review-planner:review-plan`; повторный вызов `/dex-mr-reviewer:mr-review` на том же MR смотрит только дельту.
- **Слияние -> приёмка.** Стенд принимает слитое: образ привязывается к merge-коммиту.
- **Баг -> обратно.** Причина найдена - исправление идёт реализацией или ремедиацией приёмки.

## Как команды передают работу друг другу

Каждая команда-вход возвращает результат со статусом (`complete`, `blocked`, `partial`) и решениями, принятыми за вас, с основанием. Не хватает входа - `blocked` с названием недостающего, нужный плагин или аргумент. Невыводимые бизнес-решения идут вам вопросом; равноценные технические выбираются и записываются. Результат этапа проверяется судьёй, который не писал артефакт: у дизайна и плана метки `design-quality: passed` и `plan-quality: passed` обязательны, иначе работа возвращается на доработку ([Поток вызова](/architecture/call-flow/)).

## Что взять из бандла

Один бандл покрывает часть цепочки. Например, `dotnet-developer` включает дизайн, реализацию, тесты, ревью обеих сторон и поиск багов, но не приёмку на стенде; `bug-lifecycle` - баги, инциденты, приёмку, реализацию, но не дизайн. Какой бандл что даёт, показывает [Что поставить](/start/choose/); полный состав - [каталог бандлов](/catalog/bundles/).

## Автономный вариант

Вместо этапов 2-5 можно отдать задачу трекам `dex-auto`: цель из тикета, проектирование, код с тестами, саморевью, запись в документацию и (с `--pr`) PR. Трек остаётся в рамках: push только с `--pr`, merge не делает. Приёмка, инциденты и обработка чужого ревью остаются отдельными командами.

## Правила для всей цепочки

1. Начинайте с самой дешёвой проверки, которая может остановить: требования проверяются до дизайна, дизайн до кода.
2. Не пропускайте звено с названным судьёй: проверка артефакта автором не считается.
3. Каждый этап должен оставлять артефакт на диске, чтобы следующий читал его, а не пересказ.
4. Необратимые действия (push, merge, запись в MR, мутация стенда) остаются за вами ([Границы объёма](/practices/scope-done/)).
