Один и тот же ревьюер или дебаггер работает в .NET-, TypeScript- и Python-проектах. Если бы он хранил внутри список «для .NET грузи вот это, для TypeScript - то», каждый новый стек требовал бы правки агента. Каталог решает это иначе: агент **вычисляет** нужные skills, а не хранит их список.

## Как это происходит

1. Агент загружает process-skill `dex-skill-stack-registry:stack-registry`: реестр «манифест проекта - префикс skills».
2. Определяет стек по манифесту в **затронутой папке** (монорепозиторий может быть разностековым):

   | Стек | Признаки | Префикс |
   |---|---|---|
   | `dotnet` | `*.csproj`, `*.sln`, `Directory.Build.props` | `dex-skill-dotnet-*` |
   | `ts` | `package.json`, `tsconfig.json`, `*.ts`, `*.tsx` | `dex-skill-ts-*` |
   | `python` | `pyproject.toml`, `requirements.txt`, `setup.py`, `*.py` | `dex-skill-python-*` |

3. Берёт из видимого списка доступных skills те, чьё имя начинается с префикса стека.
4. Сужает по теме задачи (симптом, ось ревью, поверхность атаки): грузится пересечение «стек x тема», а не всё семейство. Нерелевантные skills раздули бы контекст и зашумили чек-лист находками не по теме.
5. Кросс-стековые темы грузит независимо от стека: `solid`, `testability`, `kubernetes`, `observability`, `ci-gates` и skill своей платформы CI, `react` и `playwright` по теме фронтенда.

Пример: стек `dotnet` и тема «медленный запрос» - это `dex-skill-dotnet-ef-core`; тема «ложный async» - `dex-skill-dotnet-async-patterns`.

## Почему префикс имени

В Claude Code нет метаданных, по которым можно было бы сгруппировать skills по стеку, поэтому единственный признак группировки - префикс имени. Две оси не дублируют друг друга:

- **Префикс** - жёсткая ось стека: имя совпадает или нет.
- **`description`** - мягкая ось темы внутри стека: формулировки разнятся, поэтому по ней одной отбирать ненадёжно.

Автоматическая активация по описанию внутри субагента срабатывает ненадёжно, так что отбор делает сам агент явным чтением списка. Следствие для авторов: все skills одного стека обязаны нести единый префикс `dex-skill-<стек>-*`, иначе фильтр вернёт пустоту, и агент молча потеряет часть знаний.

## Что если стека или skills нет

Это не ошибка. Стека нет в реестре (мобайл, Go, Rust) - агент работает знаниями модели и тематическими skills и отмечает в отчёте, что профильных skills под стек нет. Префикс есть, но skills не установлены - фильтр даёт пусто, вызов несуществующего имени возвращает мягкую ошибку `Unknown skill`, фаза не падает. Так новый стек без skills безопасно «ничего не делает».

Покрытие стеков неравномерно: Python представлен гигиеной проекта и ML-skills, backend-тем для Python (Django, FastAPI) нет, и по ним отбор вернёт пусто. Это видно в [FAQ](/faq/).

## Добавить новый стек

1. Создать skills `dex-skill-<стек>-<тема>` ([Писать skill](/authoring/skill/)).
2. Добавить строку в реестр `dex-skill-stack-registry`.
3. Агенты не править.

Что остаётся стековым: кодеры и тестописатели несут идиомы языка в теле, и стек есть в их имени (`dotnet-coder`, `ts-test-writer`). Для них by-stack loading не нужен. Различие общих и стековых агентов - на странице [Специалисты](/concepts/specialists/), нормативное описание - [AGENT_FRAMEWORK.md](https://github.com/dex-it/ai-kit/blob/main/docs/AGENT_FRAMEWORK.md#by-stack-loading-общий-агент-грузит-профильные-skills-по-реестру).
