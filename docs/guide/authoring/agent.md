Агент (специалист) - роль, которая работает в отдельном контексте и возвращает результат вызывающему. Он дороже skill: у него есть описание в листинге, тело, предзагрузка контракта стыка и модель. Нормативный документ - [AGENT_FRAMEWORK.md](https://github.com/dex-it/ai-kit/blob/main/docs/AGENT_FRAMEWORK.md); страница объясняет путь по нему.

## Когда нужен агент, а когда нет

| Нужен агент, если | Достаточно skill или команды, если |
|---|---|
| есть несколько фаз с проверяемым результатом и переходами между ними | достаточно списка ловушек - это skill |
| работа ведётся в изолированном контексте (читает много кода, нужен сжатый возврат) | нужен один вызов человеком с аргументом - это команда |
| результат читает другой узел или команда, поэтому нужен формальный handoff | задача укладывается в несколько вызовов инструментов |
| нужна своя модель или уровень рассуждения | |

Если «команда» растёт за 200 строк и несёт несколько сценариев с гейтами, это агент ([Писать команду](/authoring/command/)).

## Как устроен агент

Агент описывается **фазами-контрактами**, а не процедурами. У фазы есть цель, наблюдаемый результат и критерий завершения; как это сделать, Claude знает сам. Причина: пошаговый текст дублирует знания модели и ломается при отклонениях, а критерий завершения проверяем.

```text
plugins/specialists/<область>/dex-<роль>/
  .claude-plugin/plugin.json
  agents/<имя>.md
  commands/<команда>.md     необязательно - точка входа в этого агента
  README.md
```

Файл агента лежит прямо в `agents/` (подкаталоги ломают адрес `{plugin}:{name}`, правило `agent-file-nested`) и называется как поле `name` (`agent-file-name-mismatch`).

### Имя

- **Стековый агент** (идиомы языка в теле) - стек в имени: `dotnet-coder`, `ts-test-writer`.
- **Общий агент** (стек грузится skills по реестру) - чистая роль: `debugger`, `mr-reviewer`, `self-reviewer`.
- Переименование агента - major-версия плагина.

## Frontmatter: поля и причины

| Поле | Статус | Что и почему |
|---|---|---|
| `name` | обязательно | совпадает с именем файла |
| `description` | обязательно | роль, области ответственности, сжатая сигнатура handoff и слово «Триггеры» с симптомами; правила - [Как писать description](/authoring/descriptions/) |
| `tools` | обязательно | перечень инструментов; нужен `Skill`, если агент грузит skills. Покрывает обязанности из тела **и** из загруженных skills: судья, пишущий метку `quality-checks`, обязан иметь `Write` или `Edit`; узел, ведущий журнал решений, - `Edit` |
| `model` | обязательно | `opus`, `sonnet`, `haiku` и другие значения платформы, не `inherit`; выбор - в разделе ниже |
| `effort` | необязательно | `low`, `medium`, `high`, `xhigh`, `max`; ставится вниз для механической работы, вверх - только с причиной в теле |
| `skills` | необязательно | предзагрузка безусловного process-skill в полной форме `{plugin}:{skill}`; у узла это `dex-skill-node-contract:node-contract` |

Чего нет: `allowed-tools` (у агентов поле `tools`), `permissionMode`, `hooks`, `mcpServers` (в агенте плагина платформа их игнорирует).

### Как выбрать model и effort

Критерий один: **тип работы**, а не предметная область.

| Тир | Когда | Сигналы |
|---|---|---|
| `opus` | высокая цена ошибки, открытое суждение | оркестрация, ревью, многошаговый поиск причины, архитектура с компромиссами |
| `sonnet` | рабочая лошадка | кодогенерация по правилам, структурированная генерация, диагностика по чек-листу |
| `haiku` | узкое шаблонное, без правок кода | заполнение по форме, чтение статуса |

`model` - потолок: агент на `sonnet` в сессии на Opus всё равно идёт на Sonnet. Явное значение нужно, чтобы дешёвая работа не гналась на дорогой модели только потому, что сессия на ней. Цена считается ходами, а не токеном за ход: дешёвая модель на многошаговой работе делает лишние итерации и может выйти дороже.

`effort` - override, а не потолок, поэтому правило асимметрично: механике ставят `low` или `medium`, открытому суждению не ставят ничего (остаётся выбор пользователя), вверх идут только с причиной, записанной в теле. Уровень подбирается прогоном на реальных задачах агента, а не копируется у соседа; при смене модели подбор повторяется. Haiku 5.5 на `low` в длинном агентном промте чаще останавливается рано; у Haiku 4.5 и ранее оси `effort` нет вовсе (`frontmatter-effort-unsupported-model`). Подробнее и с источниками: [Модель и effort](/practices/models-effort/), норма - [AGENT_FRAMEWORK, «Стоимость»](https://github.com/dex-it/ai-kit/blob/main/docs/AGENT_FRAMEWORK.md#стоимость-model-и-effort).

## Тело агента

```markdown
# Название роли

Одно-два предложения: кем выступает агент и что обеспечивает.

## Phases

Gather -> Analyze -> Prioritize -> Present.

## Phase 1: Gather

**Goal:** зачем фаза существует (достичь, а не «сделать»).

**Input (handoff):** что принимает узел: поля, блокирующие и допускающие значение по умолчанию.

**Output:** наблюдаемый артефакт фазы.

**Exit criteria:** проверяемое снаружи условие завершения.

**Mandatory:** yes

## Boundaries

Что агент не делает, когда возвращает blocked, что требует подтверждения.
```

Обязательное в теле: хотя бы одна фаза `## Phase N: <Имя>` с `**Goal:**` и `**Exit criteria:**`; в первой фазе `**Input (handoff):**`; в последней `**Output (handoff):**` (в `status` первым полем, затем поля контракта стыка и принятые решения). Каждый атрибут отделён пустой строкой от соседнего, иначе markdown слепит их в абзац (`glued-attribute-block`).

Правила содержания фазы:

- **Exit criteria наблюдаемо.** «Агент понял» или «анализ завершён» валидатор отклоняет: это внутреннее состояние. Нужен артефакт или внешний факт (тест прогнан, источник сверен).
- **Проверка опирается на внешнее.** Фаза проверки законна, пока в неё приходит новый факт извне. «Убедись ещё раз» просто складывается с собственной проверкой модели и даёт лишний проход.
- **Скиллы грузятся условно** («если стек X - загрузи Y»), а не «все на всякий случай»; безусловно предзагружается только контракт стыка.
- **Fan-out с условием объёма** («при крупном diff»), а не безусловное «запускай субагентов».
- **Пометка обязательности голая** (`**Mandatory:** yes`); условие пропуска - `optional - skip_if ...`.
- **Нет литералов путей записи артефактов**, чьё место задаёт раскладка проекта: место приходит полем входа или определяется через `project-docs-map` ([Корпус и словарь](/architecture/corpus-glossary/)).
- **Нет пошаговых процедур, документации API и кода**: процедура — признак, что фаза описана неверно.
- **Граница объёма в `Boundaries`**: что агент не делает; исход «менять нечего» для узкого агента назван допустимым ([Границы объёма](/practices/scope-done/)).

### Образец

Компактный реальный агент: `plugins/specialists/product/dex-backlog-manager/agents/backlog-manager.md` (около 6 КБ). Его начало:

```markdown
---
name: backlog-manager
description: Управляет epic-level backlog, приоритизирует задачи, ... Handoff - вход бэклог, ... Триггеры - backlog, бэклог, приоритизация, ...
tools: Read, Write, Edit, Grep, Glob, Skill
model: sonnet
skills:
  - dex-skill-node-contract:node-contract
---

# Backlog Manager

## Phases

Gather -> Analyze -> Prioritize -> Present.

## Phase 1: Gather

**Goal:** Получить текущее состояние backlog и контекст для принятия решений.

**Input (handoff):** контракт стыка - в pre-loaded `node-contract` ... Бэклога нет -> halt плюс возврат оркестратору со `status: blocked`.

**Output:** Список epics/items с их текущим статусом, возрастом, ...

**Exit criteria:** Есть полный snapshot backlog с метаданными (status, priority, age, owner). Пустые слоты помечены.
```

Что здесь показательно: `sonnet` (работа по правилам и форме), предзагружен только контракт стыка, остальные skills (`epic-planning`, `prioritization`) агент грузит в нужной фазе, `Exit criteria` называет проверяемый артефакт, отсутствие входа даёт `blocked`, а не домысел. Полный текст агента и его фазы смотрите в файле, это эталон формы.

## Контракт стыка и режимы

Каждый агент выполняет контракт стыка `dex-skill-node-contract:node-contract` (валидатор требует его предзагрузку: `frontmatter-skills-missing`). Из него следуют привычные для читателя каталога вещи: первое поле выхода `status` (`complete`, `blocked`, `partial`), недостающее возвращается, а не домысливается, решения узла перечисляются с основанием, метку `quality-checks` ставит не автор артефакта ([Поток вызова](/architecture/call-flow/)). Вопросы к человеку задаёт вызывающая команда, а не агент.

Агенты, которых вызывает скрипт трека `dex-auto`, - особый класс (узлы трека): модель и схему выхода задаёт скрипт, а валидатор их судит по сокращённому набору правил. Этот случай — для авторов самого `dex-auto`, ориентир - [components.md](https://github.com/dex-it/ai-kit/blob/main/plugins/auto/docs/components.md).

## Как проверить

```bash
node tools/validate-agent.js plugins/specialists/<область>/dex-<роль>/agents/<имя>.md
npm run validate:agents
npm run validate:node-contract
```

Типичные сообщения (в том числе восемь ошибок на агенте-«пустышке») и исправления - в [Типичных ошибках валидаторов](/authoring/validators/). Если правился `name`, каталог или состав плагина, дополнительно полезна проба видимости `node tools/run-activation.js --agents` (платный прогон, в CI не входит).

Вручную остаётся: смысл объявленной сигнатуры handoff, отсутствие дублей с skills, критерий внешнего факта в проверочных фазах, обобщённость роли.

## Чек-лист перед PR

- [ ] `name` совпадает с файлом, нет `allowed-tools`, `permissionMode`, `hooks`, `mcpServers`
- [ ] `description`: роль, области, сжатая сигнатура и «Триггеры - ...»; не больше 500 знаков, если возможно (750 - предел)
- [ ] `tools` покрывают фазы тела и загруженные skills; есть `Skill`
- [ ] явный `model`; `effort` только по необходимости
- [ ] `skills:` содержит `dex-skill-node-contract:node-contract` и ничего лишнего
- [ ] у каждой фазы `Goal` и наблюдаемый `Exit criteria`; есть `Input (handoff)` и `Output (handoff)`
- [ ] нет процедур, кода, документации API, дублей skills, литералов путей записи
- [ ] есть `Boundaries`
- [ ] запись в `marketplace.json`, README, версии, бандлы ([Плагин и бандл](/authoring/plugin-bundle/))
- [ ] `npm run precheck` зелёный
