Skill - самая лёгкая единица каталога и самая частая. Хороший skill небольшой: он называет ситуации, которые исполнитель сам не заподозрит. Нормативный документ - [SKILL_FRAMEWORK.md](https://github.com/dex-it/ai-kit/blob/main/docs/SKILL_FRAMEWORK.md); здесь объяснено, как им пользоваться.

## Когда нужен skill, а когда нет

Нужен, если модель **знает** технологию, но **не применит** правило, потому что не распознает ситуацию. Пример: документацию по `OnDelete` она читала, а каскадное удаление при soft-delete не заподозрит. Мера - прогон без skill на поручении, где ловушка не названа: провалился - skill нужен.

Не нужен, если:

- это базовые знания (синтаксис, работа библиотеки по первой странице документации) - модель их знает;
- это порядок работы с несколькими фазами и результатом - нужен агент ([Писать агента](/authoring/agent/));
- правило нужно только в одной команде или одном агенте - оно живёт в их теле;
- правило специфично для вашего проекта - его место в `CLAUDE.md` проекта или в своде правил, а не в общем каталоге. «Убрать имена проекта - правило всё ещё читается» - признак общего правила.

## Два типа skill

| | Trap-skill (по умолчанию) | Process-skill |
|---|---|---|
| Отвечает на | «какие грабли в области X» | «как действовать, что грузить, в каком порядке» |
| Содержание | чек-лист ловушек | реестр или правила, развилки решения |
| Примеры | `dotnet-ef-core`, `redis`, `kubernetes` | `stack-registry`, `project-baseline` |
| Регистрация | нигде | имя в allowlist `PROCESS_SKILLS` в `tools/validate-skill.js` и маркер `<!-- skill-type: process -->` в теле |
| Порог размера | 250 строк | 500 строк |

Тип влияет на то, как валидатор судит файл. Забытая регистрация process-skill проявляется косвенно: правило `trap-missing-triad` ругается на разделы H3 без триады.

## Где лежит и как называется

```text
plugins/skills/dex-skill-<имя>/
  .claude-plugin/plugin.json
  skills/<имя>/SKILL.md
  skills/<имя>/references/...      необязательно, детали по требованию
```

Имя плагина `dex-skill-<имя>`, имя skill внутри - `<имя>`, ссылка для императивной загрузки из агента - `dex-skill-<имя>:<имя>`. Правила имён:

- **Стековый skill** - с единым префиксом стека: `dex-skill-dotnet-ef-core`, `dex-skill-ts-nodejs-api`, `dex-skill-python-pytorch`. Префикс - единственный признак, по которому общий агент отбирает skills стека ([Загрузка по стеку](/architecture/stack-loading/)).
- **Язык-нейтральная тема** (`kafka`, `solid`, `ddd`) - без префикса стека.
- **Skill, производящий документ по стандарту** - `dex-skill-<предмет>-<стандарт>`: `system-requirements-29148`, `use-cases-cockburn`.
- **Оракул качества артефакта** - `{тип}-quality`: `requirement-quality`, `adr-quality`.

Skill, у которого потребитель один плагин, едет внутри этого плагина (`skills/<имя>/` рядом с `agents/`) и отдельной записи в каталоге не получает.

## Frontmatter: поля и причины

```yaml
---
name: redis
description: Redis - старт сервиса без Redis, промахи горячего ключа, ... Активируется при redis, distributed lock, rate limit, ...
---
```

| Поле | Статус | Зачем и ограничения |
|---|---|---|
| `name` | обязательно | имя skill; у каталога обязательное по конвенции (платформа его документирует как необязательное) |
| `description` | обязательно | единственный механизм автоматической активации; правила - в [Как писать description](/authoring/descriptions/) |
| `keywords` | запрещено | платформа его не поддерживает, ключевые слова идут внутрь `description` (`frontmatter-forbidden`) |
| прочие поля платформы (`when_to_use`, `disable-model-invocation`, `allowed-tools`, `paths` и другие) | по необходимости | перечень сверен в SKILL_FRAMEWORK, раздел «Frontmatter»; поле вне перечня платформа молча игнорирует |

Поле вне списка валидатор ловит только для `keywords`, остальное проверяет автор вручную.

## Что писать в теле

Тело trap-skill - короткая вводная («решение по документации версии из манифеста проекта») и чек-лист. Форма пункта растёт только по свидетельству прогона:

1. **Название ситуации** - по умолчанию. Часто этого достаточно.
2. **Плюс факт библиотеки**, если прогон показал, что поиск по документации его не находит. Факт сверен с первоисточником и несёт условие версии («с Npgsql 6 ...»).
3. **Плюс обязательный исход**, если исполнитель ситуацию узнал, а решение принял неверное. Исход покрывает механизм, а не подслучай, и называет все допустимые варианты.
4. **Ловушка H3 «Плохо / Правильно / Почему»** - только когда шаги 1-3 не помогли. «Правильно» - имя API или условие, а не развёрнутый код.

Причина такой лестницы: формы без свидетельства добавляют объём без прироста обнаружения ([Контекст: меньше, но невыводимое](/practices/context/)).

### Образец

Реальный skill каталога, `plugins/skills/dex-skill-redis/skills/redis/SKILL.md` (13 строк, проходит все валидаторы):

```markdown
---
name: redis
description: Redis - старт сервиса без Redis, промахи горячего ключа, потеря распределённого лока, лимит запросов на границе окон. Активируется при redis, distributed lock, rate limit, rate limiting, AbortOnConnectFail, StackExchange.Redis, ioredis, cache, TTL, sliding window, fixed window, cache stampede, sentinel
---

# Redis - чек-лист

Пункт называет ситуацию, которую исполнитель сам не заподозрит.

- Старт сервиса при недоступном Redis
- Конкурентные промахи горячего ключа идут в источник каждый
- Распределённый лок защищает запись в общий ресурс: лок может быть потерян до конца работы
- Лимит запросов в окне: всплеск на границе окон
```

Что в нём важно: ни одной строки документации Redis, каждый пункт - ситуация, а не инструкция; `description` начинается с технологии и аспектов, а за словами «Активируется при» идут 13 активаторов. Манифест рядом - `plugin.json` с именем, версией, витриной на русском и ключевыми словами.

### Чего не писать

Анти-паттерны из фреймворка, в порядке частоты: документация API вместо ловушек; развёрнутый код (лимит валидатора - 12 строк в блоке, и это потолок, а не цель); объяснение базовых концепций; шаги туториала; дубль ловушки из соседнего skill (оставьте одну, в другой дайте ссылку); привязка универсальной темы к одному инструменту («Serilog logging» вместо «Logging»); конкретика одного проекта вместо обобщённого правила.

## Пороги валидатора

Числа нормативно живут в SKILL_FRAMEWORK (разделы «Лимиты (валидатор)» и «Размер skill») и в константах `tools/validate-skill.js`:

| Что | Предел |
|---|---|
| Длина `description` | меньше 50 символов - ошибка; больше 500 - предупреждение; больше 750 - ошибка; 1536 - потолок платформы на `description` + `when_to_use`, дальше текст режется |
| Активаторы после «Активируется при» | не меньше 10 (у process-skill нарушение - предупреждение) |
| Размер trap-skill | больше 250 строк - ошибка; цель - наименьший размер при равном обнаружении |
| Размер любого skill | больше 500 строк - ошибка; больше 42 000 символов - ошибка, больше 30 000 - предупреждение |
| Блок кода | не длиннее 12 строк |
| `references/` | больше 30 000 символов на файл или на каталог - предупреждение |

Деталь, которая не нужна всегда, выносится в `references/` со ссылкой из `SKILL.md`: она не тратит контекст, пока её не прочитали.

## Как проверить

```bash
node tools/validate-skill.js plugins/skills/dex-skill-<имя>/skills/<имя>/SKILL.md
npm run validate:skills
```

Типичные сообщения и исправления - в [Типичных ошибках валидаторов](/authoring/validators/). Чего валидатор не видит и что остаётся на вашей совести: обобщённость ловушки, отсутствие документации API, отсутствие дубля с соседом.

Для skills, чей предмет - ловушки технологии, в репозитории есть испытания живым прогоном (`tests/trap-skills/`): метод и ключ ответа описаны в [tests/README.md](https://github.com/dex-it/ai-kit/blob/main/tests/README.md#метод-сжатие-по-свидетельству). Они платные и в CI не входят, но именно они дают «свидетельство» для шагов формы пункта.

## Чек-лист перед PR

- [ ] `name` и `description` есть, поля `keywords` нет
- [ ] `description`: технология и аспекты, не список ловушек и не точки входа; 10 и больше активаторов; в пределах длины
- [ ] Тело - ловушки, а не документация; нет заголовков «Как настроить» и «Что такое»
- [ ] Блоки кода короче 12 строк, «Правильно» - указатель, а не код
- [ ] Нет дубля с другим skill
- [ ] Стековый skill несёт префикс стека
- [ ] Запись в `marketplace.json`, имя в таблицах README, версия плагина и каталога ([Плагин и бандл](/authoring/plugin-bundle/))
- [ ] Skill нужен хотя бы одному бандлу? Тогда обновлены `bundle.json` и версия бандла
- [ ] `npm run precheck` зелёный
