Команда - то, что человек вызывает слэшем: `/плагин:команда`. Она решает одну задачу за вызов в текущем контексте или ведёт порядок шагов через специалистов. Нормативный документ - [COMMAND_FRAMEWORK.md](https://github.com/dex-it/ai-kit/blob/main/docs/COMMAND_FRAMEWORK.md).

## Когда нужна команда, а когда нет

| Нужна команда, если | Не команда, если |
|---|---|
| человек должен явно запустить действие с аргументом | поведение должно включаться само по теме разговора - это skill |
| действие короткое: собрать, показать статус, обернуть один CLI | нужны фазы с гейтами, свой контекст и проверка результата - это агент |
| нужен вход в работу, который ведёт порядок шагов и держит остановки на решении человека | нужно менять сам клиент - это мод |

Признаки того, что команда выросла в агента: больше одного сценария с разной логикой, гейты вида «не делай X, пока не подтвердил Y», обязательная фаза проверки после действия, глубокий скан по чек-листу со skills.

## Два жанра команд

**Точечная команда** - тонкая обёртка: цель, формат результата, границы. Пример в каталоге - команды CLI-утилит.

**Команда-вход** ведёт работу: принимает аргумент, делегирует узлам (`Agent`), спрашивает человека в нужных местах и сводит результат. Таких команд немного, это `/dex-architect:design`, `/dex-implement:implement`, `/dex-mr-reviewer:mr-review`, `/dex-business-analyst:feature`. Тело исполняет главный поток, поэтому только у команды есть канал к человеку; вызванные узлы невыводимое возвращают ей ([Поток вызова](/architecture/call-flow/)). Такая команда несёт `Agent` в `allowed-tools`.

Разница в форме тела: у точечной команды `Goal`, `Output`, `Scenarios`, `Constraints`; у команды-входа блоки `Input`, «Порядок делегирования», `Output`, `Constraints`.

## Где лежит и как вызывается

```text
plugins/specialists/<область>/dex-<плагин>/commands/<команда>.md    -> /dex-<плагин>:<команда>
plugins/utilities/dex-<имя>/commands/<команда>.md
```

Команда из `commands/` вызывается только полной формой `/<плагин>:<команда>`. Голое имя платформа даёт skill: если команду нужно звать без префикса, она оформляется как skill (`skills/<имя>/SKILL.md` с `name`), и тогда её судит `validate-command`, а не `validate-skill` (регистрация - `tools/command-skills.js`). Такие случаи единичны, дефолт - `commands/`.

Команда обычно лежит в плагине того специалиста, кому делегирует. Команда, которая сама выбирает исполнителя по манифесту репозитория (`/dex-implement:implement`, `/dex-test:test`), живёт в собственном плагине, поэтому ей нужен кодер или тестописатель вашего стека.

## Frontmatter

```yaml
---
description: Статус Kubernetes pods через kubectl
user-invocable: true
allowed-tools: Bash
argument-hint: "[-n namespace] [--label app=name] [--wide]"
---
```

| Поле | Статус | Что и почему |
|---|---|---|
| `description` | обязательно | одно предложение, различимое от соседей; лежит в листинге на каждом ходу, поэтому короткое ([Как писать description](/authoring/descriptions/)) |
| `argument-hint` | если есть аргументы | подсказка в меню команд |
| `allowed-tools` | по необходимости | **преаппрув** инструментов на ход, а не ограничение: все инструменты остаются доступными, и список ничего не доказывает о том, чего команда не делает. Ограничивает только `disallowed-tools` |
| `user-invocable`, `disable-model-invocation` | по необходимости | кто может вызывать; `disable-model-invocation` убирает описание из контекста модели |

Поведение `allowed-tools` и листинга описано в [документации skills](https://code.claude.com/docs/en/skills); сверка нормативного документа каталога от 02.09.2026. Попадание команд в бюджет листинга самой платформой явно не документировано.

## Что писать в теле

Писать: **цель** (одна фраза), **формат результата** («готово» с внешним фактом: вывод сборки, путь к файлу), **сценарии** (если их несколько), **границы** (чего команда не делает, когда останавливается; исход «ничего не менять» законен), `argument-hint`.

Не писать: bash-скрипты с конкретными командами (Claude знает `dotnet build`), справочники кодов ошибок, справочники PromQL и SQL, примеры вывода на полсотни строк, туториалы, литерал пути записи артефакта, место которого задаёт раскладка проекта (команда называет ключ и оставляет разрешение процедуре).

### Образец: точечная команда

Реальная команда `plugins/utilities/dex-kubectl-cli/commands/kube-pods.md`:

```markdown
---
description: Статус Kubernetes pods через kubectl
user-invocable: true
allowed-tools: Bash
argument-hint: "[-n namespace] [--label app=name] [--wide]"
---

# /kube-pods

Показать статус pods в Kubernetes кластере через kubectl.

**Goal:** Список pods с их статусом, рестартами, ресурсами.

**Output:** Таблица: name, status, restarts, age, node. С `--wide` -- IP, resource usage (cpu/memory).

**Scenarios:**

- Без аргументов -- pods в default namespace
- `-n namespace` -- pods в конкретном namespace

**Constraints:**

- Требует `kubectl` с настроенным доступом к кластеру
- Если kubectl не найден или нет доступа -- показать инструкцию установки
```

Показательно: нет ни одной команды `kubectl` в тексте (модель сама выберет), результат описан форматом, границы названы.

### Образец: команда-вход

`plugins/specialists/qa/dex-test/commands/test.md` (`/dex-test:test`) устроена так: `Input` (аргумент, по умолчанию незакоммиченный diff), «Порядок делегирования» (матрица осей покрытия на месте, написание тестов отдаётся тестописателю стека, замер покрытия и добор), `Output` (тесты, покрытие с названием отрезанных осей, статус прогона) и `Constraints` (порог покрытия не занижается молча). Нет тестописателя нужного стека в установке - команда возвращает `blocked` с именем недостающего плагина и сама тесты не пишет. Смотрите файл как эталон формы; `/dex-stand-reviewer:review-stand` и `/dex-mr-reviewer:mr-review` показывают то же с санкцией на запись (до команды `пушь` ничего не публикуется).

## Размеры

| Что | Предел | Правило |
|---|---|---|
| цель для точечной команды | 20-50 строк | ориентир, валидатор не проверяет |
| потолок точечной команды | 80 строк | `size-exceeds-recommended` |
| потолок команды конвейера (`mr-analyze`, `mr-apply`) | 100 строк | допуск по allowlist `PIPELINE_COMMANDS` |
| жёсткий потолок | 200 строк | `size-exceeds-hard-limit`: «это должен быть агент с фазами» |
| блок кода | 5 строк | `code-fence-too-long` |

Команда, упёршаяся в потолок, обычно несёт справочник или процедуру, которую нужно вырезать, либо это агент.

## Как проверить

```bash
node tools/validate-command.js plugins/<путь>/commands/<команда>.md
npm run validate:commands
```

Что ловит валидатор: нет `description` (`frontmatter-required`), тело - bash-скрипт (`bash-script-detected`), тело - процедура вместо цели (`procedural-body`), оформлено как документация (`documentation-style-title`), размер, ссылки на несуществующие `{plugin}:{skill}` и на `docs/` каталога. Расшифровка - в [Типичных ошибках валидаторов](/authoring/validators/).

## Чек-лист перед PR

- [ ] есть `description` (одно предложение) и `argument-hint`, если принимаются аргументы
- [ ] есть цель и формат результата; для команды-входа - `Input`, порядок делегирования, границы
- [ ] нет bash-скриптов, справочников ошибок и запросов, длинных шаблонов вывода
- [ ] границы названы: что не делает, когда останавливается (`blocked` с причиной), что требует санкции
- [ ] все названные `{plugin}:{skill}` существуют, документов `docs/` каталога нет
- [ ] размер в пределе своего типа
- [ ] запись плагина в `marketplace.json`, README, версии, бандл (если команда из бандла называет новый артефакт, он должен ехать в том же бандле)
- [ ] `npm run precheck` зелёный
