Мод - единственная единица каталога, которая меняет не то, что модель читает, а то, что делает и показывает сам Claude Code: панель, строку над вводом, перехват вызова инструмента. Это TypeScript, который клиент исполняет в собственном процессе. Нормативные документы: [MOD_FRAMEWORK.md](https://github.com/dex-it/ai-kit/blob/main/docs/MOD_FRAMEWORK.md) и справка выбора механизма [EXTENSION_MECHANISMS.md](https://github.com/dex-it/ai-kit/blob/main/docs/EXTENSION_MECHANISMS.md).

## Когда нужен мод

| Задача | Механизм |
|---|---|
| событие, скрипт, текст в контекст или блок (линтер после правки, запрет команды, уведомление) | обычный хук-команда в утилите: проще, стабильнее |
| живая панель, строка состояния, перехват с логикой, состояние на сессию, свои команды | **мод** |
| Claude Code как часть вашего продукта (CI-бот, сервис) | Agent SDK, вне каталога |
| доступ модели к внешней системе | MCP-сервер или CLI-утилита |

Цена выбора мода: API function hooks в раннем доступе и меняется между релизами без предупреждения, ошибка валит сессию пользователя (у обычного хука срывается один вызов). Поэтому мод берут, когда нужен интерфейс или перехват, а не ради удобства.

В каталоге хук-команда и мод в одном плагине не смешиваются: категория выводится по признаку, и плагин с обоими читался бы как мод. Нужны оба поведения - два плагина. Моды не входят в бандлы.

## Как устроен мод

```text
mods/dex-<имя>/
  .claude-plugin/plugin.json   манифест: витрина + userConfig
  hooks/
    hooks.json                 { "description": ..., "modules": ["./register.tsx"] }
    register.tsx               точка входа: export const register: Register
    *.ts                       остальные части (импорты точки входа)
  tests/*.test.ts              прогон чистой части
  README.md                    установка, использование, пределы
```

Хук - функция `($, e, next)`: `$` - разрешённые эффекты (`$.process.run`, `$.http.fetch`, `$.ui.*`, `$.store`, `$.clock`), `e` - событие, `next` - продолжение цепочки. Моды вкладываются как middleware. Точка входа экспортирует `register(on, options)`: `on` регистрирует хуки, `options` - значения полей `userConfig`.

Реальный образец: `mods/dex-github-pr-tracker/`. Начало `hooks/register.tsx` — это карта: какие события мод слушает (`session.start`, `ui.render`, `command.run`, `prompt.submit`, `tool.call`, `turn.complete`) и что на каждое делает. Решения и тексты вынесены в `.ts` без `$` (`args.ts`, `github.ts`, `poll.ts`, `text.ts`), и именно они покрыты тестами в `tests/`.

### userConfig

Настройки объявляются в `plugin.json` и правятся через `/config`. У каждого поля обязательный `title`; типы `string`, `number`, `boolean`, `directory`, `file`; можно задать `default`, `min` и `max` для чисел, `options` для выбора. Пример из мода слежения за PR:

```json
"pollSeconds": {
  "type": "number",
  "title": "Poll interval, seconds",
  "description": "Период опроса GitHub. Минимум 15 секунд.",
  "default": 60,
  "min": 15,
  "max": 3600
}
```

Границу числа держите полем (`min`), а не одной прозой README, и дублируйте зажимом в коде. Секреты читайте из окружения (`$.env.get`), а поле заводите, когда окружения нет.

## Правила состава, продиктованные инструментами

- **Относительные импорты несут расширение** `.ts` или `.tsx`: иначе `node --test` не найдёт цепочку.
- **В `.tsx` держите только отрисовку и точку входа**, решения - в `.ts` без `$`. Причина: Node не берёт `.tsx`, а модуль, трогающий `$`, прогоном не берётся вовсе (живого `$` нет).
- **Всё, что мод показал человеку, он обязан уметь отдать текстом** (команда печатает то же в транскрипт): иначе модель работает вслепую рядом с панелью.
- **Первый опрос ничего не объявляет**, иначе взятый под наблюдение объект вываливает историю целиком; периодический опрос имеет нижний порог и не ходит в сеть в headless-режиме `-p`.
- **Чужой текст** (заголовки, комментарии, имена веток) чистится от управляющих символов до отрисовки.
- **Ошибка источника видна фактом, который можно исправить** («glab не установлен»), а не пустой панелью.

## Как проверять

Валидаторы каталога читают markdown и json и в TypeScript не заходят, поэтому мод закрывается другими средствами:

| Что | Команда | Что ловит |
|---|---|---|
| типы | `npm run typecheck:mods` | разъезд с контрактом API (входит в `npm run validate`) |
| чистая часть | `npm run test:mods` | разбор, сборка ответа, дельта, тексты для модели |
| манифест и модуль | `claude plugin validate --strict mods/<имя>` | форму `plugin.json`, `userConfig`, перечень хукнутых событий и вызовов `$` (нужен установленный клиент, в CI не ходит) |
| живой прогон | `claude -p "/<команда>" --plugin-dir mods/<имя>` | загрузку модуля и путь до ответа |
| живая сессия | `claude --plugin-dir mods/<имя>` | отрисовку, таймеры, кнопки |

Контракт типов `mods/types/claude-code.d.ts` — копия деклараций, которые пишет сам движок; при обновлении клиента его перегенерируют (как - в MOD_FRAMEWORK, раздел «Инструментарий»).

## Оформление в каталоге

Запись в `marketplace.json` с `category: mod`, описание в витрине README (раздел «Моды»), версия мода и каталога ([Плагин и бандл](/authoring/plugin-bundle/)). Категорию задаёт ключ `modules` в `hooks.json`, несоответствие ловит `catalog-category-mismatch`.

## Чек-лист перед PR

- [ ] `hooks.json` называет ровно одну точку входа, она экспортирует `register`
- [ ] каждый вызов `$`, перечисленный `claude plugin validate`, мод действительно делает
- [ ] ошибки источника данных видны пользователю, пустой панели нет
- [ ] первый опрос тихий, есть нижний порог периода, в `-p` сети нет
- [ ] чужой текст очищен, показанное доступно текстом
- [ ] импорты с расширением, в `.tsx` только отрисовка
- [ ] `npm run typecheck:mods`, `npm run test:mods`, `claude plugin validate --strict mods/<имя>` без ошибок
- [ ] живой прогон отвечает данными
- [ ] запись каталога, README, версии синхронны
